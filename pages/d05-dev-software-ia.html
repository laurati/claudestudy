Disciplina 05

Desenvolvimento de Software com IA

Usar IA para escrever código é fácil. Difícil é fazê-la escrever o que você realmente precisa. O segredo está em preparar ambiente, contexto e prompts.

Ao finalizar esta disciplina você será capaz de:

  • Estruturar um fluxo de desenvolvimento IA-driven
  • Reduzir erros com geração automatizada de testes e refatorações
  • Usar IA para debugging, análise de logs e identificação de falhas
  • Criar rules, contextos e memories que guiam a IA com precisão
  • Integrar ferramentas como Cursor, Copilot e servidores MCP no seu dia a dia

Fundamentos do desenvolvimento IA-driven

No desenvolvimento IA-driven, a IA deixa de ser um "autocomplete esperto" e passa a ser um par de programação que lê o projeto, executa comandos, roda testes e propõe mudanças. O dev assume o papel de tech lead do agente.

Os três modos de uso

ModoExemploQuando
Autocomplete (inline)Sugestões enquanto digita (Tab)Código repetitivo, boilerplate
Chat / edição guiada"Explique esta função", "refatore este trecho"Dúvidas, mudanças localizadas
Agente"Implemente a feature X e rode os testes"Tarefas multi-arquivo (Disciplina 06)

O ciclo básico: Explorar → Planejar → Implementar → Verificar

  1. Explorar: peça para a IA ler os arquivos relevantes e explicar o que existe — sem escrever código ainda.
  2. Planejar: peça um plano com os arquivos a alterar e os testes; revise e corrija o plano.
  3. Implementar: em passos pequenos.
  4. Verificar: testes, lint, tipos, revisão do diff. Só então commit.
A documentação do Claude Code descreve exatamente esse fluxo em Best practices e Common workflows. O ponto central: dê à IA uma forma de verificar o próprio trabalho (testes, screenshots, comandos).

Exemplo: "onboarding" da IA num projeto existente

Você está entrando neste projeto agora. Sem alterar nada:
1. Explique a arquitetura em alto nível (módulos, fluxo de uma requisição).
2. Liste comandos de build, teste e lint (encontre-os nos arquivos de config).
3. Identifique convenções: tratamento de erro, logs, injeção de dependência, testes.
4. Aponte 3 arquivos que são bons exemplos de "como fazemos aqui".
Ao final, proponha o conteúdo de um CLAUDE.md com essas informações.

No Claude Code, o comando /init faz uma versão automática disso e cria o CLAUDE.md inicial.

Biblioteca de prompts para desenvolvimento

Transforme os prompts que funcionam em comandos reutilizáveis. No Claude Code, arquivos Markdown em .claude/commands/ (ou skills em .claude/skills/) viram comandos /nome; no Cursor, rules acionadas manualmente; no Copilot, prompt files.

Exemplo: comando /novo-endpoint (Claude Code)

<!-- .claude/commands/novo-endpoint.md -->
---
description: Cria endpoint REST seguindo os padrões do projeto
argument-hint: [recurso] [verbo]
---
Crie o endpoint $ARGUMENTS.
1. Siga o padrão de src/orders/ (controller → service → repository).
2. Valide a entrada com o DTO + class-validator.
3. Escreva testes unitários do service e um teste e2e do endpoint.
4. Atualize docs/openapi.yaml.
5. Rode `npm test` e `npm run lint` e corrija até passar.

Categorias para sua biblioteca: explicar código, gerar testes, revisar PR, refatorar, debugar, gerar migração, documentar, escrever commit/PR, investigar incidente.

Estruturação de documentação para contexto

O agente começa cada sessão "do zero". A documentação de contexto diz a ele o essencial do projeto. Hierarquia recomendada:

~/.claude/CLAUDE.md ← preferências pessoais (todas as sessões) repo/CLAUDE.md ← visão geral, comandos, convenções (versionado, do time) repo/src/payments/CLAUDE.md ← regras específicas daquele módulo (carregado quando relevante) repo/docs/ ← PRDs, ADRs, FDDs (referenciados, lidos sob demanda)

Exemplo: CLAUDE.md enxuto e eficaz

# Projeto: API de Pedidos

## Comandos
- `make dev` sobe API + Postgres (docker compose)
- `make test` roda testes; `make test-one T=TestNome` roda um teste
- `make lint` deve passar antes de qualquer commit

## Arquitetura
- Hexagonal: domain/ (puro, sem I/O) → app/ (casos de uso) → adapters/ (http, db, llm)
- Decisões em docs/adr/ — respeite os ADRs com status accepted

## Convenções
- Erros: retorne `apperr.New(code, msg)`; nunca `panic` fora de main
- Logs estruturados com slog; nunca logue dados de cartão ou CPF
- Testes table-driven; mocks só para adapters

## Cuidado
- Migrações em db/migrations são imutáveis depois de mergeadas: crie uma nova
- Não altere arquivos em gen/ (gerados por `make gen`)
Menos é mais: cada linha do CLAUDE.md custa contexto em todas as sessões. Inclua só o que o agente erraria sem saber. Veja Manage Claude's memory.

Geração de Rules e Memories

Rules são instruções persistentes (geralmente escritas por você) que se aplicam a todo o projeto ou a um conjunto de arquivos. Memories são fatos que a ferramenta lembra entre sessões (alguns aprendidos automaticamente a partir das suas correções).

Exemplo: rule do Cursor com escopo por arquivos

---
description: Padrões para componentes React
globs: ["src/components/**/*.tsx"]
alwaysApply: false
---
- Componentes funcionais com props tipadas (interface XxxProps)
- Estilo com Tailwind; não criar arquivos .css
- Estados de loading/erro sempre tratados
- Exemplo de referência: src/components/OrderCard.tsx

Exemplo: instruções do Copilot

<!-- .github/copilot-instructions.md -->
Este repositório usa Go 1.23, chi para HTTP e sqlc para acesso a dados.
Ao gerar SQL, edite db/queries/*.sql e rode `make gen`; nunca escreva SQL inline.
Testes devem usar testcontainers para Postgres.

Gerando rules com a própria IA

Revise os últimos 20 PRs mergeados e os comentários de code review.
Extraia as regras implícitas que os revisores cobram repetidamente
e escreva-as como rules concisas (uma linha cada, com o porquê).
Ignore o que o linter já garante.
No Claude Code você pode adicionar memórias rapidamente durante a sessão (ex.: pedindo "lembre que…" ou editando com /memory). Revise periodicamente: regras contraditórias confundem o agente.

Testes automatizados e detecção de Edge Cases

A IA é muito boa em enumerar casos de borda que esquecemos. Use-a em duas etapas: primeiro listar casos, depois escrever testes.

Exemplo: descoberta de edge cases

Para a função calcularFrete(cep, pesoKg, itens) liste casos de borda agrupados em:
entradas inválidas, limites numéricos, formatos (CEP com/sem hífen),
regras de negócio (frete grátis, regiões remotas), concorrência/tempo,
falhas de dependências (API dos Correios fora do ar).
Para cada caso: entrada, comportamento esperado e se já é coberto pelos testes atuais.
  • Property-based testing (Hypothesis, fast-check): peça à IA para propor propriedades ("o frete nunca é negativo", "ordenar duas vezes = ordenar uma vez").
  • Mutation testing (Stryker, mutmut): mede se seus testes detectam bugs plantados — ótimo para avaliar testes gerados por IA.
  • Cuidado: a IA pode escrever testes que validam o comportamento atual (inclusive bugs) ou que "passam por construção". Revise as asserções.

Servidores MCP para desenvolvimento e Docker Catalog

Servidores MCP dão ao assistente acesso a ferramentas e dados externos: banco de dados, GitHub, navegador (Playwright), documentação atualizada (Context7), Figma, Sentry, Jira…

Exemplo: adicionando servidores MCP no Claude Code

# servidor local via stdio (npx)
claude mcp add playwright -- npx @playwright/mcp@latest

# servidor remoto via HTTP
claude mcp add --transport http context7 https://mcp.context7.com/mcp

# listar / verificar
claude mcp list
// .mcp.json (escopo de projeto, versionado para o time)
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://readonly@localhost/app"]
    }
  }
}

Docker MCP Catalog e Toolkit

O Docker MCP Catalog reúne servidores MCP empacotados como imagens verificadas; o MCP Toolkit do Docker Desktop permite ativá-los com um clique, isolados em containers, gerenciar segredos e conectá-los a clientes (Claude, Cursor, VS Code) por meio de um gateway único.

Segurança: um servidor MCP executa código e pode expor dados. Use servidores de fontes confiáveis, credenciais de somente leitura quando possível, e lembre que conteúdo trazido por MCP (issues, páginas) pode conter prompt injection.

Processos de debugging otimizados

Debugging com IA funciona quando você fornece evidência e exige método:

  1. Reproduza o bug (idealmente com um teste que falha).
  2. Forneça: mensagem de erro completa, stack trace, entrada que causa o problema, o que mudou recentemente (git log/git diff).
  3. Peça hipóteses ranqueadas e como testar cada uma, antes de qualquer correção.
  4. Corrija a causa raiz, não o sintoma; mantenha o teste como regressão.

Exemplo: prompt de debugging

O teste TestCheckout_Concurrent falha ~1 em 10 execuções com:
<erro>duplicate key value violates unique constraint "payments_order_id_key"</erro>
1. Leia checkout/service.go e payments/repo.go.
2. Liste até 3 hipóteses para a falha intermitente, da mais à menos provável.
3. Para cada uma, proponha um experimento (log, teste) que a confirme ou descarte.
4. Só depois de confirmar, proponha a correção mínima.
git bisect + IA: para regressões, peça à IA que escreva o script de teste usado no git bisect run — encontra o commit culpado automaticamente.

Boas práticas de Refactoring

  • Testes primeiro: sem rede de proteção, não há refatoração — só "reescrita com fé".
  • Passos pequenos e commits frequentes: facilita revisar e reverter. Peça explicitamente "um passo por vez".
  • Separe refatoração de mudança de comportamento (PRs diferentes).
  • Diga o padrão alvo com exemplo ("transforme no formato de src/orders/service.ts").
  • Refatorações em massa: prefira ferramentas determinísticas (codemods, LSP rename, OpenRewrite) e use a IA para escrever o codemod ou tratar os casos que a ferramenta não cobre.
  • Checkpoints: ferramentas como o Claude Code permitem voltar ao estado anterior de uma edição (checkpointing) — mas o Git continua sendo seu checkpoint principal.

Análise automatizada de logs e debugging

LLMs são ótimos para encontrar padrões em grandes volumes de logs, correlacionar eventos e resumir. Cuidados: logs podem conter dados sensíveis (mascare antes) e podem ser enormes (filtre/agregue antes de enviar).

Exemplo: pipeline de logs para o Claude Code em modo não interativo

# últimos erros do serviço, agregados, enviados ao agente (modo headless -p)
kubectl logs deploy/checkout --since=1h \
  | grep -E "ERROR|WARN" \
  | sed -E 's/[0-9]{3}\.[0-9]{3}\.[0-9]{3}-[0-9]{2}/***CPF***/g' \
  | sort | uniq -c | sort -rn | head -200 \
  | claude -p "Agrupe estes erros por causa provável, estime o impacto e sugira o próximo passo de investigação para cada grupo."

Ver modo headless do Claude Code. Em produção, ferramentas de observabilidade já trazem assistentes de IA para consultas em linguagem natural (Disciplina 10).

Verificação de vulnerabilidades

Código gerado por IA pode introduzir vulnerabilidades clássicas (SQL injection, segredos hardcoded, validação ausente) e dependências inexistentes ou maliciosas ("slopsquatting": a IA sugere um pacote que não existe e alguém o registra). Defesa em camadas:

CamadaFerramentas
SAST (código)Semgrep, CodeQL, SonarQube
Dependências (SCA)Dependabot, Renovate, npm audit, govulncheck, Trivy, OSV-Scanner
Segredosgitleaks, trufflehog, push protection do GitHub
Revisão assistidaComando /security-review do Claude Code; prompts de revisão focados em OWASP
Containers/IaCTrivy, Checkov

Exemplo: prompt de revisão de segurança

Revise o diff com foco exclusivo em segurança (OWASP Top 10):
injeção, authn/authz, exposição de dados, SSRF, desserialização, segredos.
Para cada achado: severidade, linha, cenário de exploração concreto e correção.
Não reporte achados teóricos sem caminho de exploração plausível.
Verifique também se todas as dependências novas existem e são as oficiais.

Exercícios e quiz

Exercício — prepare um repositório seu para IA
  1. Rode /init (Claude Code) ou peça o "onboarding" e revise o CLAUDE.md gerado, cortando o supérfluo.
  2. Crie 3 comandos reutilizáveis (teste, review, novo endpoint).
  3. Configure 1 servidor MCP útil (banco somente leitura ou Context7).
  4. Implemente uma feature pequena com o ciclo explorar → planejar → implementar → verificar e compare com o tempo habitual.
1. Qual o fator mais importante para a IA acertar em tarefas de código?
Com verificação, o agente itera até acertar; sem ela, você vira o "testador manual".
2. O que NÃO deveria ir para o CLAUDE.md?
O que uma ferramenta determinística garante não precisa consumir contexto.
