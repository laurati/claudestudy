Protocolos de comunicação: MCP e A2A

Não adianta ter agente, modelo e ferramenta se eles não se integram. MCP conecta a IA a dados e ferramentas; A2A conecta agentes a outros agentes — mesmo de tecnologias diferentes.

Ao finalizar esta disciplina você será capaz de:

  • Garantir comunicação entre agentes e sistemas com tecnologias diferentes
  • Conectar a IA a dados e ferramentas externas com eficiência
  • Criar servidores MCP como parte do seu ambiente de desenvolvimento
  • Integrar agentes, APIs e sistemas sem limitações de tecnologia
  • Criar aplicações prontas para ecossistemas com múltiplos agentes

Protocolos de comunicação × Tool Calling

🎯 Objetivo

Entender a diferença entre o modelo pedir para chamar uma função (tool calling) e um protocolo que padroniza como ferramentas são oferecidas a qualquer aplicação de IA.

🧩 Para que serve

Decidir onde a integração deve morar: dentro da sua aplicação (tool calling direto) ou num servidor reutilizável por vários clientes (MCP).

✅ Quando usar
  • Tool calling direto: a ferramenta só existe para uma aplicação (ex.: "consultar pedido" no seu chatbot).
  • Protocolo (MCP): a mesma integração vai servir Claude Code, Cursor, um agente interno etc.
⛔ Quando evitar / cuidados

Não crie um servidor MCP para uma função de 10 linhas usada por um único sistema — é infraestrutura a mais para manter. E lembre: protocolo não substitui uma boa descrição de tool.

Tool calling (function calling) é um recurso do modelo/API: você descreve funções no request e o modelo pede para chamá-las. Mas cada aplicação precisa implementar cada integração do zero — N aplicações × M ferramentas = N×M integrações.

Um protocolo padroniza a conversa entre aplicações de IA e provedores de capacidades. Com MCP, quem escreve um servidor (ex.: GitHub) o faz uma vez, e qualquer cliente compatível (Claude, Cursor, Copilot, ADK…) pode usá-lo: N + M em vez de N×M.

Tool callingMCP
NívelFormato de request/response de uma API de LLMProtocolo cliente-servidor (JSON-RPC 2.0)
Onde a ferramenta viveNo código da sua aplicaçãoNum servidor reutilizável (local ou remoto)
DescobertaEstática (você lista no request)Dinâmica (tools/list, notificações de mudança)
Além de ferramentasNãoResources, prompts, sampling, elicitation

MCP usa tool calling por baixo: o cliente converte as tools do servidor em definições de tool para o modelo.

Exemplo prático: a mesma integração, duas abordagens

Cenário: três aplicações (chatbot de suporte, Claude Code dos devs e um agente de vendas) precisam consultar o status de pedidos.

  • Só tool calling: cada aplicação define sua tool consultar_pedido, implementa a chamada à API, autenticação e tratamento de erro. Três implementações para manter; quando a API muda, três correções.
  • Com MCP: o time de pedidos publica um servidor MCP pedidos com a tool consultar_pedido. As três aplicações apenas se conectam a ele. Mudou a API? Corrige-se o servidor.

Analogia: tool calling é cada aparelho vir com seu próprio carregador; MCP é a tomada USB-C — o fabricante do periférico implementa uma vez e funciona em qualquer aparelho compatível.

Fundamentos do MCP (Tools, Resources e Prompts)

🎯 Objetivo

Conhecer as três primitivas do MCP (tools, resources, prompts), os papéis (host, cliente, servidor) e os transportes (stdio, Streamable HTTP).

🧩 Para que serve

Saber o que expor em cada primitiva: tools = ações que o modelo decide chamar; resources = dados que a aplicação/usuário anexa como contexto; prompts = templates que o usuário escolhe (viram comandos /).

✅ Quando usar

Ao desenhar qualquer servidor MCP ou ao avaliar um servidor de terceiros antes de instalá-lo.

⛔ Quando evitar / cuidados

Não exponha tudo como tool: ler um arquivo de configuração estático é melhor como resource (não gasta uma volta de raciocínio do modelo). Tools com efeitos colaterais devem pedir confirmação.

O Model Context Protocol foi criado pela Anthropic (2024) e hoje é um padrão aberto adotado amplamente. Papéis:

  • Host: a aplicação de IA (Claude Desktop, Claude Code, IDE).
  • Client: o conector dentro do host que mantém uma conexão 1:1 com um servidor.
  • Server: expõe capacidades.
PrimitivaQuem controlaO que éExemplo
ToolsO modelo decide chamarFunções que executam ações ou consultascriar_issue, executar_query
ResourcesA aplicação/usuário escolhe incluirDados para contexto, identificados por URIfile:///docs/api.md, db://schema/orders
PromptsO usuário invocaTemplates de interação reutilizáveis"/revisar-pr", "/analisar-incidente"

Primitivas do lado do cliente: sampling (o servidor pede ao cliente uma geração de LLM), roots (escopo de diretórios) e elicitation (o servidor pede informação ao usuário).

Exemplo: mensagens JSON-RPC (simplificadas)

// cliente → servidor: quais ferramentas você tem?
{"jsonrpc": "2.0", "id": 1, "method": "tools/list"}

// servidor → cliente
{"jsonrpc": "2.0", "id": 1, "result": {"tools": [{
  "name": "buscar_pedido",
  "description": "Busca um pedido pelo ID",
  "inputSchema": {"type": "object", "properties": {"pedido_id": {"type": "string"}}, "required": ["pedido_id"]}
}]}}

// cliente → servidor: o modelo decidiu chamar
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "buscar_pedido", "arguments": {"pedido_id": "PED-123"}}}

Transportes

  • stdio: servidor local como subprocesso. Simples e seguro para ferramentas na máquina do dev.
  • Streamable HTTP: servidor remoto via HTTP, com streaming opcional (SSE) e autorização OAuth 2.1. Para servidores compartilhados/SaaS.

Servidores MCP e Docker MCP Toolkit

🎯 Objetivo

Saber encontrar, avaliar e rodar servidores MCP prontos, inclusive de forma isolada com o Docker MCP Toolkit.

🧩 Para que serve

Dar "superpoderes" ao assistente sem escrever código: acesso ao banco, ao GitHub, ao navegador, à documentação atualizada de bibliotecas.

✅ Quando usar

Quando a integração já existe pronta e é mantida por uma fonte confiável (fornecedor oficial, catálogo verificado).

⛔ Quando evitar / cuidados

Servidores de origem desconhecida rodando via npx com suas credenciais têm o mesmo risco de instalar um pacote aleatório. Prefira imagens verificadas e credenciais somente leitura.

Há milhares de servidores prontos: sistemas de arquivos, Git/GitHub, bancos (Postgres, SQLite), navegadores (Playwright), Slack, Notion, Figma, Sentry, Stripe, documentação (Context7)… Consulte o registro oficial no site do MCP e o Docker MCP Catalog.

O Docker MCP Toolkit (no Docker Desktop) roda servidores como containers isolados, gerencia segredos e expõe tudo por um gateway único ao qual você conecta seus clientes — menos configuração e mais isolamento do que rodar npx de pacotes diretamente na máquina.

Como escolher e avaliar um servidor MCP

  1. Origem: é oficial do fornecedor (GitHub, Sentry, Stripe…) ou está num catálogo verificado? Quantas pessoas usam? Tem manutenção recente?
  2. Escopo: quais tools ele expõe? Alguma escreve/apaga dados? Dá para desativar tools individuais?
  3. Credenciais: crie um token só para ele, com o mínimo de permissão (ex.: token do GitHub só leitura em 1 repositório).
  4. Isolamento: rode em container (Docker MCP Toolkit) quando possível.

Exemplo: servidores úteis por tipo de tarefa

TarefaServidorO que você ganha

MCPs na prática, incluindo Resources e Prompts

🎯 Objetivo

Usar MCP no dia a dia: adicionar servidores ao cliente, referenciar resources com @, chamar prompts como comandos e usar MCP direto pela API.

🧩 Para que serve

Trazer contexto externo (issue, schema do banco, página da doc) para a conversa sem copiar e colar, e transformar fluxos repetidos em comandos.

✅ Quando usar

Sempre que você se pegar colando o mesmo tipo de informação no chat (tickets, logs, schema).

⛔ Quando evitar / cuidados

Cada servidor ativo adiciona descrições de tools ao contexto. Muitos servidores ligados ao mesmo tempo = mais tokens e mais chance de o modelo escolher a tool errada. Ative só o necessário por projeto.

Exemplo: configurando servidores no Claude Code

# stdio
claude mcp add github -- docker run -i --rm -e GITHUB_PERSONAL_ACCESS_TOKEN ghcr.io/github/github-mcp-server
# HTTP remoto
claude mcp add --transport http sentry https://mcp.sentry.dev/mcp

# dentro da sessão:
#   /mcp                         → status e autenticação dos servidores
#   @servidor:recurso            → referencia um RESOURCE como contexto
#   /mcp__servidor__prompt       → executa um PROMPT do servidor

> /mcp__github__resumir_issue 482          ← PROMPT do servidor (template)

Desenvolvimento de servidores MCP

🎯 Objetivo

Construir um servidor MCP próprio com o SDK oficial (Python/TypeScript), com tools bem descritas, validação e tratamento de erro.

🧩 Para que serve

Expor um sistema interno da sua empresa (ERP, API de pedidos, base de conhecimento) uma única vez para todos os clientes de IA.

✅ Quando usar

Quando não existe servidor pronto, quando o servidor existente expõe demais (você quer um subconjunto seguro) ou quando precisa aplicar regras de negócio/permissões.

⛔ Quando evitar / cuidados

Não espelhe sua API REST 1:1 ("um endpoint = uma tool"). Modele tools pela tarefa do usuário (ex.: resumo_do_cliente em vez de 5 chamadas GET) e devolva respostas enxutas.

SDKs oficiais existem para Python, TypeScript, Go, Java, C#, Kotlin e outras. Em Python, o FastMCP (incluído no SDK) transforma funções decoradas em primitivas.

Exemplo: servidor MCP com tools, resources e prompts (Python)

# pip install "mcp[cli]"
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("pedidos")

PEDIDOS = {"PED-123": {"status": "ENVIADO", "itens": ["notebook"], "cliente": "Ana"}}

@mcp.tool()
def buscar_pedido(pedido_id: str) -> dict:
    """Busca status e itens de um pedido pelo ID (formato PED-123)."""
    if pedido_id not in PEDIDOS:
        return {"erro": f"Pedido {pedido_id} não existe. Verifique o formato PED-NNN."}
    return PEDIDOS[pedido_id]

@mcp.resource("pedidos://politica-cancelamento")
def politica() -> str:
    """Política de cancelamento vigente."""
    return "Pedidos PAGOS podem ser cancelados em até 24h. Pedidos ENVIADOS não."

@mcp.prompt()
def analisar_reclamacao(texto: str) -> str:
    """Template para analisar reclamações de clientes."""
    return f"Analise a reclamação, identifique o pedido, consulte-o e proponha uma resposta:\n\n{texto}"

if __name__ == "__main__":
    mcp.run()                                  # stdio (padrão)
    # mcp.run(transport="streamable-http")     # servidor HTTP
# testar com o MCP Inspector (interface para chamar tools/resources/prompts)
mcp dev servidor.py

# registrar no Claude Code
claude mcp add pedidos -- python servidor.py
Boas práticas: descrições excelentes (são o "prompt" da tool); validação de entrada; erros acionáveis; respostas enxutas; paginação; permissões mínimas; logs no stderr (no stdio, o stdout é o canal do protocolo!); autenticação OAuth em servidores remotos.

Deploy e distribuição utilizando Docker

🎯 Objetivo

Empacotar e distribuir servidores MCP em containers, localmente (stdio) ou remotamente (HTTP), com segredos e versionamento.

🧩 Para que serve

Garantir que o servidor rode igual na máquina de todos os devs e em produção, isolado do sistema de arquivos e da rede do host.

✅ Quando usar

Ao compartilhar o servidor com o time/empresa, ao publicar num catálogo ou ao rodar servidores remotos acessados por vários usuários.

⛔ Quando evitar / cuidados

Servidores remotos precisam de autenticação (OAuth) e autorização por usuário — nunca exponha na internet um servidor com credenciais de serviço compartilhadas e sem controle de acesso.

Exemplo: Dockerfile para o servidor

FROM python:3.12-slim
WORKDIR /app
RUN pip install --no-cache-dir "mcp[cli]"
COPY servidor.py .
RUN useradd -m mcp
USER mcp
ENTRYPOINT ["python", "servidor.py"]
docker build -t minhaorg/mcp-pedidos:1.0 .
# uso via stdio por qualquer cliente:
claude mcp add pedidos -- docker run -i --rm minhaorg/mcp-pedidos:1.0

Distribuição: publique a imagem num registry (Docker Hub, GHCR), versione semanticamente, documente variáveis de ambiente e permissões. Para servidores remotos, implante como serviço HTTP (Cloud Run, Kubernetes) atrás de autenticação.

Segurança MCP: servidores podem ser maliciosos (exfiltração, descrições de tool com instruções escondidas — "tool poisoning") ou ser vetor de prompt injection (dados que retornam). Use fontes confiáveis, fixe versões, isole em containers, conceda o mínimo de credenciais e revise as permissões pedidas.

Google A2A (Agent to Agent): fundamentos

🎯 Objetivo

Entender o que o A2A resolve: agentes de times, fornecedores e frameworks diferentes colaborando sem expor sua implementação.

🧩 Para que serve

Delegar uma tarefa inteira a outro agente (que tem suas próprias ferramentas, memória e regras) como se fosse um colega, e não chamar uma função.

✅ Quando usar

Quando o "outro lado" é autônomo, demora, pode pedir mais informação ou pertence a outro time/empresa (ex.: agente de viagens de um fornecedor).

⛔ Quando evitar / cuidados

Se o que você precisa é uma operação determinística (consultar saldo), use uma tool/MCP — A2A acrescenta latência, ciclo de vida de task e custo de outro LLM.

O A2A é um protocolo aberto (iniciado pelo Google em 2025, hoje sob a Linux Foundation) para que agentes opacos — construídos com frameworks e fornecedores diferentes, sem expor sua lógica interna, memória ou ferramentas — colaborem como pares. Baseado em padrões web: HTTP, JSON-RPC 2.0 e SSE para streaming (com variantes gRPC/REST nas versões mais novas), além de push notifications via webhook para tarefas longas.

MCPA2A
ConectaAgente → ferramentas e dadosAgente ↔ agente
ContraparteFunções com esquema (previsíveis)Agente autônomo (pode negociar, pedir mais informação, demorar)
Unidade de trabalhoChamada de toolTask com ciclo de vida

Em termos simples: MCP é como dar uma ferramenta a um funcionário (uma calculadora, acesso ao sistema). A2A é como pedir ajuda a outro departamento: você explica o que precisa, eles trabalham do jeito deles, podem voltar com perguntas e depois entregam o resultado. Você não sabe (nem precisa saber) quais ferramentas eles usaram.

Exemplo: quando usar MCP e quando usar A2A no mesmo sistema

Um agente de planejamento de viagens corporativas:

  • Consulta a política de viagens da empresa → MCP (resource/tool de leitura, resposta determinística).
  • Pede a um agente de reservas do fornecedor que encontre o melhor voo dentro do orçamento → A2A: o fornecedor tem lógica própria, pode demorar, pode responder "não há voo nesse horário, aceita o das 14h?" (estado input-required).
  • Pede ao agente de finanças (outro time, feito em outro framework) a aprovação do gasto → A2A.

Tasks, Messages, Parts, Agent Cards e Artifacts

🎯 Objetivo

Dominar o vocabulário do A2A: Agent Card, Task, Message, Part e Artifact.

🧩 Para que serve

Ler e escrever mensagens A2A corretamente e saber onde fica cada informação (pedido, conversa, resultado).

✅ Quando usar

Sempre que for consumir ou expor um agente via A2A — esses objetos aparecem em toda requisição.

⛔ Quando evitar / cuidados

Não confunda Message (conversa, inclusive perguntas intermediárias) com Artifact (o entregável final). Coloque o resultado em artifacts para que o cliente saiba o que é "produto".

  • Agent Card: "cartão de visitas" JSON do agente remoto — nome, descrição, URL, capacidades (streaming, push), habilidades (skills), formatos aceitos e esquema de autenticação.
  • Task: unidade de trabalho com ID e estado; pode durar segundos ou dias.
  • Message: um turno de comunicação (role: user ou agent) composto de Parts.
  • Part: pedaço de conteúdo tipado — texto, arquivo ou dados estruturados.
  • Artifact: resultado/produto gerado pela task (relatório, imagem, JSON), também composto de Parts.

Exemplo: os cinco conceitos numa única interação

1. Orquestrador lê o AGENT CARD do "agente-de-relatorios"
   → descobre a skill "relatorio_vendas" que aceita application/json
2. Envia uma MESSAGE (role: user) com duas PARTS:
     - TextPart: "Gere o relatório trimestral com destaque por região"
     - DataPart: {"trimestre": "2026-Q3", "moeda": "BRL"}
3. O agente remoto cria a TASK  t-91  (state: working)
4. Responde com MESSAGE (role: agent): "Incluo devoluções?"  (state: input-required)
5. Orquestrador responde na mesma task: "Sim"               (state: working)
6. Task t-91 → completed, com dois ARTIFACTS:
     - "relatorio.pdf"   (FilePart)
     - "resumo"          (DataPart: {"total": 1250000, "maior_regiao": "Sudeste"})

Arquitetura e fluxo de comunicação A2A

🎯 Objetivo

Entender a sequência completa: descoberta → envio → acompanhamento (polling, streaming ou push) → resultado.

🧩 Para que serve

Escolher o modo de interação certo para cada tipo de tarefa e implementar o cliente sem travar à espera de respostas.

✅ Quando usar
  • message/send: tarefas rápidas.
  • message/stream (SSE): o usuário acompanha o progresso.
  • Push notifications (webhook): tarefas de minutos/horas.
⛔ Quando evitar / cuidados

Não segure uma conexão HTTP aberta por horas esperando uma task longa; use push notifications e consulte a task por ID (tasks/get).

Cliente A2A (agente orquestrador) Servidor A2A (agente remoto) 1. GET /.well-known/agent.json ──────────────► devolve Agent Card 2. escolhe skill adequada 3. message/send (ou message/stream) ──────────► cria Task (submitted → working) ◄────────── status updates (SSE) / artifacts parciais 4. se input-required: envia nova Message na mesma Task ◄────────── Task completed + Artifacts

Exemplo: requisição JSON-RPC message/send (simplificada)

POST https://agente-viagens.exemplo.com/a2a

Estrutura de uma Task e estados possíveis

🎯 Objetivo

Conhecer o ciclo de vida da Task e seus estados, inclusive os terminais.

🧩 Para que serve

Implementar corretamente o cliente: saber quando esperar, quando responder ao agente (input-required), quando autenticar e quando desistir.

✅ Quando usar

Ao construir orquestradores, dashboards de acompanhamento e lógica de retry/timeout.

⛔ Quando evitar / cuidados

Não trate input-required como erro: é o agente remoto pedindo uma informação. E não reenvie uma task terminal (completed, failed…) — crie uma nova.

Exemplo: Task concluída (simplificada)

{
  "id": "task-789",
  "contextId": "ctx-42",
  "status": { "state": "completed", "timestamp": "2026-11-18T14:03:00Z" },
  "history": [ /* mensagens trocadas */ ],
  "artifacts": [{
    "artifactId": "art-1",
    "name": "reserva",
    "parts": [{ "kind": "data", "data": { "hotel": "Hotel Alfama", "total": 560, "moeda": "EUR" } }]
  }]
}
EstadoSignificado
submittedRecebida, ainda não iniciada
workingEm processamento
input-requiredO agente remoto precisa de mais informação do cliente
auth-requiredPrecisa de autenticação/autorização adicional
completedConcluída com sucesso (terminal)
failedFalhou (terminal)
canceledCancelada (terminal)
rejectedO agente recusou a tarefa (terminal)

Exemplo: cliente que trata os estados corretamente (pseudocódigo Python)

task = client.send_message(msg)
while task.status.state not in {"completed", "failed", "canceled", "rejected"}:
    if task.status.state == "input-required":
        # o agente remoto fez uma pergunta: mostre ao usuário (ou responda via LLM)
        resposta = perguntar_ao_usuario(task.status.message)
        task = client.send_message(nova_msg(resposta, task_id=task.id, context_id=task.context_id))
    elif task.status.state == "auth-required":
        task = client.send_message(credenciais_para(task), task_id=task.id)
    else:  # submitted / working
        time.sleep(2)
        task = client.get_task(task.id)

if task.status.state == "completed":
    for art in task.artifacts:
        salvar(art)
else:
    registrar_falha(task)   # failed / canceled / rejected

Tipos de mensagens e partes (text, file, json)

🎯 Objetivo

Saber montar mensagens com os três tipos de Part: texto, arquivo e dados estruturados (JSON).

🧩 Para que serve

Enviar ao agente remoto exatamente o formato que ele entende melhor (ex.: JSON validável em vez de texto livre) e receber resultados processáveis por código.

✅ Quando usar

Use DataPart sempre que o outro lado for processar campos (datas, valores, IDs); FilePart para PDFs, imagens, planilhas; TextPart para instruções em linguagem natural.

⛔ Quando evitar / cuidados

Evite embutir JSON dentro de texto ("segue o JSON: {...}"): o agente remoto terá de "adivinhar" o parse. E verifique no Agent Card quais formatos ele aceita.

{ "kind": "text", "text": "Resumo da análise..." }

{ "kind": "file", "file": { "name": "contrato.pdf", "mimeType": "application/pdf",
                            "uri": "https://.../contrato.pdf" } }      // ou "bytes" em base64

{ "kind": "data", "data": { "cpf_valido": true, "score": 712 } }        // JSON estruturado

A negociação de formatos acontece pelo Agent Card (defaultInputModes/defaultOutputModes, por exemplo text/plain, application/json), permitindo que agentes se adaptem ao que o outro suporta — inclusive UI e mídia.

Exemplo prático: escolhendo o tipo de Part

Você quer que o agente de RH analise um currículo para uma vaga:

  • TextPart: "Avalie a aderência deste candidato à vaga e destaque lacunas."
  • FilePart: o PDF do currículo (mimeType: application/pdf).
  • DataPart: {"vaga_id": "BE-204", "senioridade": "pleno", "requisitos": ["Go", "Postgres", "Kubernetes"]}

O artifact de retorno também vem como DataPart ({"aderencia": 0.78, "lacunas": ["Kubernetes"]}), que seu sistema grava direto no ATS sem precisar interpretar texto.

Descoberta de agentes (agent.json)

🎯 Objetivo

Publicar e consumir Agent Cards para que agentes se encontrem automaticamente.

🧩 Para que serve

Permitir que um orquestrador descubra o que cada agente sabe fazer (skills), como autenticar e quais formatos usar, sem configuração manual.

✅ Quando usar

Ao expor qualquer agente A2A, e em empresas com muitos agentes (crie um registro/catálogo interno que indexa os cards).

⛔ Quando evitar / cuidados

O Agent Card é público por natureza: não coloque nele segredos, URLs internas sensíveis ou detalhes de implementação. Use o extended card autenticado para informações restritas.

Por convenção, o Agent Card é publicado num caminho bem conhecido do domínio do agente: /.well-known/agent.json (nas versões mais recentes da especificação, /.well-known/agent-card.json). Também é possível descobrir agentes via registros/catálogos corporativos.

Exemplo: Agent Card

{
  "name": "Agente de Viagens",
  "description": "Pesquisa e reserva hotéis e voos.",
  "url": "https://agente-viagens.exemplo.com/a2a",
  "version": "1.2.0",
  "capabilities": { "streaming": true, "pushNotifications": true },
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "securitySchemes": { "oauth": { "type": "oauth2" } },
  "skills": [
    {
      "id": "reservar-hotel",
      "name": "Reservar hotel",
      "description": "Encontra e reserva hotéis dado destino, datas e orçamento.",
      "tags": ["viagem", "hotel"],
      "examples": ["Hotel em Lisboa de 10 a 14/12 até 150€"]
    }
  ]
}

Por que um caminho "bem conhecido"? É a mesma ideia de robots.txt ou /.well-known/openid-configuration: qualquer cliente sabe onde procurar sem combinar nada antes. Basta saber o domínio do agente.

Na prática em empresas: além do well-known, mantenha um registro de agentes (um serviço simples que lista os Agent Cards aprovados). O orquestrador consulta o registro, filtra por skill e por permissão do usuário, e só então chama o agente.

Composição de agentes de frameworks diferentes

🎯 Objetivo

Montar sistemas multiagente combinando agentes de frameworks diferentes (ADK, LangGraph, CrewAI, Claude Agent SDK) via A2A, cada um usando MCP para suas ferramentas.

🧩 Para que serve

Reaproveitar agentes que já existem em outros times/fornecedores, sem reescrevê-los nem acoplar-se à tecnologia deles.

✅ Quando usar

Organizações grandes, integrações B2B entre agentes, e quando cada domínio (RH, finanças, suporte) tem dono próprio.

⛔ Quando evitar / cuidados

Num único time e codebase, subagentes do próprio framework são mais simples e baratos. Cada salto A2A soma latência, custo e um ponto de falha.

O valor do A2A aparece em ambientes heterogêneos: o agente de RH foi feito com LangGraph por um time, o de finanças com ADK por outro, um fornecedor oferece um agente de viagens próprio. Um orquestrador descobre seus Agent Cards e delega tarefas sem conhecer a implementação de nenhum.

  • O ADK tem suporte nativo para expor agentes via A2A e consumir agentes remotos como subagentes.
  • SDKs oficiais do A2A (Python, JS, Java, Go, .NET) permitem "embrulhar" agentes de qualquer framework (LangGraph, CrewAI, Claude Agent SDK) num servidor A2A.
  • Combine: A2A entre agentes + MCP de cada agente para suas ferramentas.
Pontos de atenção: autenticação entre agentes (OAuth, mTLS), autorização por skill, limites de custo/tempo por task, rastreamento distribuído (propagar trace IDs entre agentes), e tratar a saída de um agente remoto como não confiável (prompt injection entre agentes).

Exemplo de arquitetura: atendimento de uma seguradora

┌──────────────────────────────┐ Cliente ─────► │ Orquestrador (Claude Agent SDK) │ └───────┬───────────┬──────────┘ A2A │ │ A2A ┌───────────────▼──┐ ┌────▼──────────────────┐ │ Agente de Sinistros│ │ Agente de Pagamentos │ │ (LangGraph, time A)│ │ (Google ADK, time B) │ └───────┬───────────┘ └────┬──────────────────┘ MCP │ MCP │ sistema de apólices, gateway de pagamento, vistoria com fotos ERP financeiro

O orquestrador não sabe que um agente usa LangGraph e o outro ADK: só conhece os Agent Cards. Cada time evolui seu agente (troca de modelo, novas tools) sem quebrar os demais, desde que mantenha as skills publicadas.
