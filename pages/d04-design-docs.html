Disciplina 04

Design Docs com IA

Documentar não é mais opcional: é como a IA entende o que você quer construir. Um bom documento é, ao mesmo tempo, alinhamento para o time e contexto para o agente.

Ao finalizar esta disciplina você será capaz de:

  • Criar documentações que aumentam a efetividade da IA
  • Entender os diferentes tipos de design docs na engenharia de software
  • Gerar e manter documentação técnica com apoio da IA
  • Registrar decisões técnicas de forma clara e objetiva
  • Transformar documentação em ativo técnico para o time e para a IA

Fundamentos de Design Docs

🎯 Objetivo

Entender o que é um design doc, como estruturá-lo (por quê → o quê → como → riscos) e por que ele virou também contexto para agentes de IA.

🧩 Para que serve

Alinhar o time antes de codar, registrar o raciocínio por trás das escolhas e dar ao agente de código instruções precisas e verificáveis.

✅ Quando usar

Em mudanças que levam mais de alguns dias, afetam outros times, envolvem trade-offs relevantes ou serão implementadas por agentes.

⛔ Quando evitar / cuidados

Não escreva design doc para mudança pequena e óbvia (corrigir bug, ajustar texto). Um documento que ninguém lê nem atualiza é só burocracia.

Estruturação

Um design doc responde, em ordem: por que (problema e contexto), o quê (objetivos, escopo, requisitos), como (solução proposta, alternativas, trade-offs) e e daí (riscos, plano de rollout, métricas de sucesso). Estrutura mínima:

1. Contexto e problema
2. Objetivos e não-objetivos
3. Proposta (com diagramas)
4. Alternativas consideradas
5. Riscos, segurança, custos
6. Plano de implementação / rollout
7. Métricas de sucesso
8. Perguntas em aberto

Objetivos e escopo

Os não-objetivos são tão importantes quanto os objetivos: eles impedem que o escopo cresça e — com IA — evitam que o agente "vá além" e implemente o que ninguém pediu.

Ferramentas

Docs-as-code (Markdown no repositório + revisão por PR) é o formato mais amigável para IA, porque o agente lê os arquivos diretamente. Complementos: Mermaid/PlantUML/Structurizr para diagramas, Notion/Confluence/Google Docs para colaboração com áreas não técnicas, e assistentes de IA para gerar rascunhos.

Design Docs na era da IA

Mudou o leitor: além de pessoas, agentes de código leem os documentos para executar tarefas. Consequências:

  • Precisão vale mais que prosa bonita: nomes exatos de módulos, comandos, contratos.
  • Critérios de aceite verificáveis viram os "testes" do agente.
  • Documentos menores e modulares (um por feature/decisão) cabem melhor no contexto do que um documento gigante.
  • O custo de escrever caiu (a IA gera rascunhos); o valor de revisar e decidir subiu.

Documentação como contexto

Ferramentas como o Claude Code carregam automaticamente arquivos de memória do projeto (CLAUDE.md) e outros leem AGENTS.md, .cursor/rules etc. O que estiver documentado ali vira comportamento padrão do agente. Ver Claude Code — Memory e AGENTS.md.

Regra prática: se você explicou algo duas vezes para a IA, documente. Se o documento não muda o comportamento do agente, ele é ruído — corte.

Formatos de documentação

🎯 Objetivo

Conhecer os tipos de documento (PRD, TRD, FRD, stories, RFC, ADR, guidelines, C4, runbook, playbook, postmortem) e o papel de cada um.

🧩 Para que serve

Escolher o documento certo para cada pergunta: o que construir (PRD), como (design/RFC), por que decidimos (ADR), como operar (runbook).

✅ Quando usar

Use a tabela como mapa: diante de uma necessidade, pergunte "quem vai ler e para tomar qual decisão?" e escolha o formato correspondente.

⛔ Quando evitar / cuidados

Não crie todos os documentos para todo projeto. Um time pequeno pode viver com PRD enxuto + ADRs + README/CLAUDE.md.

FRD (Functional Requirements Document)Detalhamento das funcionalidades: regras, fluxos, validações.

Exemplo: a mesma feature passando por vários documentos

Feature: "pagamento via Pix no checkout".

  1. PRD: problema (40% dos clientes abandonam por não ter cartão), objetivo (aumentar conversão em 10%), escopo, não-objetivos (Pix parcelado fica fora).
  2. User stories: "Como cliente, quero pagar com QR Code Pix para concluir a compra sem cartão" + critérios de aceite.
  3. RFC: "integrar com o PSP A ou B?" — aberta para comentários por uma semana.
  4. ADR-0012: "Usaremos o PSP B por suportar webhooks idempotentes" (decisão tomada).
  5. FDD + diagrama de sequência: checkout → PSP → webhook → confirmação do pedido.
  6. Runbook: "o que fazer quando o webhook do Pix parar de chegar".
  7. Postmortem (se algo der errado): linha do tempo, causa e ações.

Documentos de Produto (PRDs)

🎯 Objetivo

Escrever PRDs (de produto e de feature) com problema, público, objetivos, requisitos, critérios de aceite e métricas, usando IA para acelerar.

🧩 Para que serve

Garantir que todos — inclusive o agente que vai implementar — entendam o que e por que antes do como.

✅ Quando usar

No início de um produto ou de uma feature relevante; no fluxo SDD, o PRD é a entrada para a spec e o plano.

⛔ Quando evitar / cuidados

Não deixe a IA inventar requisitos: ela gera rascunho a partir das suas respostas. PRD sem métricas de sucesso e sem não-objetivos vira lista de desejos.

PRDs de alto nível e PRDs de feature

  • PRD de alto nível: visão do produto, público, problemas, objetivos de negócio, principais capacidades, roadmap macro.
  • PRD de feature: uma funcionalidade específica, com fluxos, requisitos e critérios de aceite detalhados — é o insumo direto para a especificação técnica e para o agente.

Principais seções de um PRD

# PRD — <nome>
## 1. Contexto e problema        (dados, evidências, quem sofre)
## 2. Objetivos / Não-objetivos
## 3. Personas e jornadas
## 4. Requisitos funcionais       (RF-01, RF-02… numerados!)
## 5. Requisitos não funcionais   (desempenho, segurança, acessibilidade)
## 6. Critérios de aceite         (Given/When/Then)
## 7. Métricas de sucesso         (KPIs, como medir)
## 8. Dependências e riscos
## 9. Fora de escopo / futuro
## 10. Perguntas em aberto

Exemplos práticos de PRD

Exemplo: trecho de PRD de feature

# PRD — Cancelamento de pedido pelo app
## Problema
32% dos contatos no SAC são pedidos de cancelamento simples (dados de jan–mar).
## Objetivos
- Permitir cancelamento self-service em até 24h após a compra.
- Reduzir contatos de cancelamento no SAC em 50% em 3 meses.
## Não-objetivos
- Cancelamento parcial de itens. Reembolso via PIX (fase 2).
## Requisitos funcionais
RF-01 O botão "Cancelar pedido" aparece só para pedidos com status PAGO e < 24h.
RF-02 O usuário escolhe um motivo (lista fixa) antes de confirmar.
RF-03 Após confirmar, o estoque é liberado e o estorno é solicitado ao gateway.
## Critérios de aceite
Dado um pedido PAGO criado há 2h, quando o usuário confirma o cancelamento,
então o status vira CANCELADO e um e-mail de confirmação é enviado.
Dado um pedido ENVIADO, então o botão não é exibido.

Design e Arquitetura

🎯 Objetivo

Produzir HLD (visão do sistema) e FDD (desenho de uma feature) com apoio de IA e deep research.

🧩 Para que serve

Decidir a solução técnica com alternativas e trade-offs explícitos, antes de gastar tempo implementando.

✅ Quando usar
  • HLD: sistema novo ou mudança estrutural (novo serviço, troca de banco).
  • FDD: feature que toca vários módulos ou tem riscos técnicos.
  • Deep research: quando você não conhece bem as opções (ex.: comparar bancos vetoriais).
⛔ Quando evitar / cuidados

Não aceite a primeira arquitetura que a IA sugerir: peça alternativas, trade-offs e riscos, e confira as fontes do deep research.

High Level Design Document (HLD)

Visão macro da solução: contexto do sistema, componentes/containers, integrações, fluxos principais, decisões de tecnologia, requisitos não funcionais e como serão atendidos (escala, disponibilidade, segurança), estimativas de capacidade e custo.

Feature Design Doc (FDD)

O "como" de uma feature: mudanças de API (contratos), modelo de dados (migrações), diagramas de sequência, tratamento de erros, feature flags, plano de testes e de rollout. É o documento que um agente de código consegue transformar em plano de implementação.

Deep Research aplicada à geração de documentos técnicos

Ferramentas de deep research (pesquisa agêntica em várias fontes) ajudam na fase de levantamento: comparar bancos vetoriais, reunir benchmarks, levantar padrões de mercado, ler documentação de APIs de terceiros. Use para gerar o anexo de pesquisa do HLD — sempre conferindo as fontes citadas.

Diagramas com IA

🎯 Objetivo

Criar diagramas C4 e Mermaid (fluxo, sequência, classe, ER, estado) como código, gerados e mantidos com IA.

🧩 Para que serve

Comunicar arquitetura e fluxos visualmente, com diagramas versionados no Git que a IA consegue ler e atualizar.

✅ Quando usar
  • C4 Context/Container: explicar o sistema para quem chega.
  • Sequência: integrações e fluxos com várias chamadas.
  • ER: modelagem de dados.
  • Estado: ciclos de vida (pedido, pagamento).
⛔ Quando evitar / cuidados

Não desenhe o nível "Code" do C4 à mão (fica velho em dias — gere da IDE se precisar). Diagrama com 40 caixas não comunica: divida.

Diagramas C4: System Context, Containers, Component e Code

O modelo C4 (Simon Brown) descreve arquitetura em quatro níveis de zoom, como um mapa:

  1. System Context: seu sistema como uma caixa, com usuários e sistemas externos.
  2. Containers: aplicações e armazenamentos que compõem o sistema (API, SPA, banco, fila).
  3. Components: módulos dentro de um container.
  4. Code: classes/funções (geralmente gerado pela IDE; raramente vale mantê-lo à mão).

Architecture Decision Record (ADR)

🎯 Objetivo

Registrar decisões de arquitetura em ADRs curtos (contexto, decisão, consequências) e manter seu ciclo de vida (proposto, aceito, substituído).

🧩 Para que serve

Preservar o porquê das decisões: novos membros e agentes de IA entendem o motivo e não "desfazem" escolhas conscientes.

✅ Quando usar

Para decisões difíceis de reverter ou que alguém vai questionar depois: banco de dados, provedor de LLM, padrão de autenticação, estrutura de módulos.

⛔ Quando evitar / cuidados

Não faça ADR para escolhas triviais e reversíveis (nome de variável, lib de data). E não edite um ADR aceito — crie outro que o substitui.

Estrutura clássica de um ADR e MADRs

Formato clássico de Michael Nygard: Título, Status, Contexto, Decisão, Consequências. O MADR (Markdown Any Decision Records) acrescenta drivers de decisão, opções consideradas e prós/contras de cada uma.

Exemplo: ADR no formato MADR

---
status: accepted
date: 2026-03-10
deciders: [laura, time-plataforma]
supersedes: ADR-0007
---
# ADR-0012: Usar pgvector em vez de banco vetorial gerenciado

## Contexto e problema
Precisamos de busca semântica para ~2M chunks no assistente de suporte.

## Drivers de decisão
- Já operamos PostgreSQL com alta disponibilidade
- Necessidade de filtros por tenant e transações com dados relacionais
- Orçamento limitado

## Opções consideradas
1. pgvector  2. Pinecone  3. Qdrant self-hosted

## Decisão
Escolhemos **pgvector**, porque atende ao volume com índice HNSW,
reaproveita operação e backup existentes e permite JOIN com permissões.

## Consequências
- Bom: sem novo fornecedor; consistência transacional.
- Ruim: escalar além de ~50M vetores exigirá reavaliação (ver gatilho abaixo).
- Gatilho de revisão: p95 de busca > 150ms ou > 20M vetores.

Status, metadados e fluxos

Status típicos: proposed → accepted | rejected → (mais tarde) deprecated ou superseded by ADR-XXXX. ADRs são imutáveis: não se edita a decisão, cria-se um novo ADR que substitui o anterior. Metadados úteis: data, decisores, links para RFC/PRD/PR, tags.

Quando usar, quando são opcionais e quando evitar

  • Use: decisões difíceis de reverter ou com impacto amplo (banco, linguagem, protocolo, padrão de integração, provedor de LLM, estratégia de autenticação).
  • Opcional: decisões locais e baratas de mudar (biblioteca de datas de um módulo).
  • Evite: usar ADR como ata de reunião, tutorial ou documentação de API; ADRs para decisões triviais (vira ruído e ninguém lê).

Engineering Guidelines

🎯 Objetivo

Escrever engineering guidelines (stack, padrões de código, testes, PRs, review) que valham para humanos e agentes.

🧩 Para que serve

Tornar o "jeito do time" explícito para que a IA gere código no padrão do projeto e o review foque no que importa.

✅ Quando usar

Ao iniciar um projeto, ao receber pessoas novas e sempre que um mesmo comentário de review se repetir.

⛔ Quando evitar / cuidados

Não escreva no guideline o que uma ferramenta já garante (formatter, linter): automatize com pre-commit e economize contexto.

Guidelines na era da IA

Guidelines viram instruções executáveis para agentes: o que antes era um wiki que ninguém lia agora é carregado em todo prompt. Por isso devem ser curtas, específicas e verificáveis. E o que puder ser checado por ferramenta (lint, formatação, tipos) deve ser checado por ferramenta — não por instrução.

Seções sugeridas de um guideline

# Engineering Guidelines
## Stack e versões            (linguagem, frameworks, banco, infra)
## Comandos                   (build, test, lint, rodar local)
## Estrutura do projeto       (onde fica o quê)
## Padrões de código          (nomes, erros, logs, injeção de dependência)
## Testes                     (pirâmide, onde ficam, cobertura mínima, o que mockar)
## Git e PRs                  (branches, commits convencionais, template de PR)
## Code review                (o que bloqueia, o que é sugestão)
## Segurança                  (segredos, validação, dependências)
## Coisas que NÃO fazer       (com o porquê)

Automação da documentação

🎯 Objetivo

Automatizar a geração e a manutenção da documentação com comandos, skills, CI e agentes agendados.

🧩 Para que serve

Evitar documentação desatualizada — que para a IA é contexto errado — sem depender da memória das pessoas.

✅ Quando usar

Em times com documentação como contexto (CLAUDE.md, ADRs, OpenAPI) e em projetos com muitas mudanças por semana.

⛔ Quando evitar / cuidados

Não publique documentação gerada sem revisão humana. E não gere doc "de enfeite" (comentário que repete o código).

Geração automatizada de documentações e criação de assistentes de IA

  • Docs de API geradas a partir de OpenAPI/código; changelogs a partir de commits convencionais.
  • Comandos/skills reutilizáveis no agente ("/gerar-adr", "/atualizar-readme") — ver Claude Code Skills e slash commands.
  • Assistente de documentação: um agente com acesso ao repositório e ao template que entrevista o autor e gera o rascunho.

Manutenção e atualização de documentações com IA

Documentação desatualizada é pior que nenhuma — para a IA, é contexto errado. Estratégias:

  • Docs no mesmo PR que o código: um job de CI pede para o agente checar se o diff exige atualização de docs (README, OpenAPI, ADR) e comenta no PR.
  • Revisões periódicas: agente agendado compara docs com código e abre issues de divergência.
  • Donos por documento (CODEOWNERS) e data de última revisão.

Exemplo: GitHub Action que pede revisão de docs ao Claude

# .github/workflows/docs-check.yml  (ver docs oficiais do Claude Code GitHub Actions)
name: docs-check
on: pull_request
jobs:
  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Verifique se as mudanças deste PR exigem atualizar README, docs/ ou ADRs.
            Se sim, comente no PR listando o que mudar. Não faça commits.

2. Contexto e alternativas: extraia da conversa e do código relevante; não invente.
3. Liste consequências positivas e negativas.
4. Se substituir um ADR anterior, atualize o status dele para "Substituído por ADR-XXXX".
5. Status inicial: "Proposto". Mostre o arquivo e pergunte se pode salvar.

Exercícios e quiz

Exercício — pacote de documentação de uma feature

Escolha uma feature real do seu trabalho. Usando IA como entrevistadora, gere: PRD de feature → FDD com diagrama de sequência Mermaid → 1 ADR → atualização do CLAUDE.md/AGENTS.md. Depois peça a um agente para implementar só com esses documentos e avalie: o que faltou nos docs?

1. Uma decisão registrada num ADR aceito mudou. O que fazer?
ADRs são imutáveis: o histórico de "por que decidimos X na época" é justamente o valor.
2. Qual nível do C4 mostra API, SPA, banco e fila como caixas separadas?
Containers = unidades executáveis/implantáveis e armazenamentos.
3. Por que "não-objetivos" são especialmente úteis quando um agente vai implementar?
Limites explícitos reduzem retrabalho e mudanças não solicitadas.
