Disciplina 06

Desenvolvimento em modo Agente

Chega de ver a IA destruir o código bom que ela mesma escreveu. Aqui você aprende a pilotar agentes com planos, especificações, gates, subagentes e um harness bem projetado.

Ao finalizar esta disciplina você será capaz de:

  • Pilotar a IA em modo agente com mais controle e confiança
  • Usar um workflow com IA que pode te deixar até 5x mais produtivo
  • Criar planos de ação que evitam perda de contexto
  • Quebrar tarefas em etapas claras para a IA seguir
  • Usar ciclos de verificação para reduzir falhas e retrabalho

Fundamentos do Desenvolvimento Agêntico

🎯 Objetivo

Entender como um agente de código trabalha sozinho por várias etapas: quebra de tarefas, estado entre sessões, verificação e correção.

🧩 Para que serve

Delegar tarefas inteiras (não só trechos) ao agente, com resultados que você consegue confiar e revisar.

✅ Quando usar

Tarefas bem definidas que tocam vários arquivos e têm critério de pronto verificável (testes, build, comportamento observável).

⛔ Quando evitar / cuidados

Tarefas ambíguas, exploratórias ou de alto risco (migração de dados em produção) pedem você no comando, com o agente em modo de sugestão.

Um agente de código roda em loop: lê arquivos, decide uma ação (editar, rodar comando, buscar), observa o resultado, decide a próxima — até considerar a tarefa concluída. Ele é poderoso e também propenso a: perder o fio em tarefas longas, declarar vitória cedo, "consertar" testes em vez do código, e mexer no que não devia.

Task Breakdown

Quebrar o trabalho em tarefas pequenas, independentes e verificáveis. Uma boa tarefa para agente cabe numa sessão, tem um critério de pronto objetivo e toca em poucos arquivos.

Exemplo: plano quebrado em tarefas

Feature: cancelamento de pedido
[ ] T1 Migração: coluna cancel_reason + índice        → pronto: migração roda e reverte
[ ] T2 Domínio: Pedido.podeCancelar() + testes         → pronto: 6 testes unitários passando
[ ] T3 Caso de uso CancelarPedido (estorno via port)   → pronto: testes com fake do gateway
[ ] T4 Endpoint POST /orders/:id/cancel + OpenAPI      → pronto: teste e2e 200/409
[ ] T5 Botão no app + estados de loading/erro          → pronto: teste Playwright do fluxo
Dependências: T1→T3, T2→T3→T4→T5

Gerenciamento de estado

O contexto do agente é volátil (compacta, reinicia). O estado da tarefa deve viver em artefatos persistentes: arquivo de plano com checkboxes, arquivo de progresso (PROGRESS.md), lista de features em JSON, commits frequentes no Git com mensagens descritivas. Assim, uma nova sessão retoma de onde a anterior parou.

Verificação, análise e correção de discrepâncias

Depois de cada passo, compare o que foi feito com o que foi especificado: o diff toca só os arquivos previstos? Os critérios de aceite estão cobertos? Há TODOs esquecidos? Peça ao agente (ou a um subagente revisor) uma análise de discrepâncias e corrija antes de seguir.

Criação e execução automatizada de testes

Testes são o "sensor" do agente. Instrua-o a escrever o teste primeiro (que falha), implementar, e rodar a suíte relevante a cada mudança. Proíba explicitamente alterar testes existentes para fazê-los passar — sem autorização.

Spec-Driven Development (SDD)

🎯 Objetivo

Aplicar o Spec-Driven Development: PRD → especificação → plano de tasks → implementação guiada pela spec.

🧩 Para que serve

Trocar o "vibe coding" por um processo em que a spec é a fonte da verdade, revisada por você antes do código existir.

✅ Quando usar

Features médias e grandes, trabalho que vai ser paralelizado entre agentes e qualquer coisa que outra pessoa precise revisar depois.

⛔ Quando evitar / cuidados

Para correções pequenas, o overhead de PRD + spec não se paga. Spec que ninguém revisa só move o problema de lugar.

Em SDD, a especificação é o artefato principal: você escreve (com ajuda da IA) o que e por que, revisa, e o agente implementa a partir dela. Ferramentas como o GitHub Spec Kit formalizam o fluxo specify → plan → tasks → implement.

Os 3 níveis do SDD

NívelDescriçãoCiclo de vida da spec
1. Spec-firstA spec é escrita antes e guia a implementação daquela tarefa.Pode ser descartada depois.
2. Spec-anchoredA spec é mantida junto ao código e atualizada a cada evolução da feature.Viva; referência para manutenção.
3. Spec-as-sourceA spec é a fonte; o código é (re)gerado a partir dela e não é editado à mão.Principal artefato; código é derivado.

Do PRD à especificação e plano (Spec-writer)

PRD (o quê / por quê, produto) ↓ spec-writer SPEC (comportamento, contratos, critérios de aceite, casos de borda) ↓ planner PLAN (abordagem técnica, arquivos, ordem, riscos) ↓ TASKS (unidades pequenas e verificáveis) → implementação → verificação

O spec-writer é um prompt/agente que lê o PRD e o código existente e produz a especificação técnica, marcando ambiguidades como perguntas em vez de inventar respostas.

Skills para geração de PRD e especificação

Encapsule o processo em skills reutilizáveis (pastas com SKILL.md + templates + scripts) — ex.: prd-writer, spec-writer, task-planner. O agente carrega a skill sob demanda quando a tarefa pede. Ver a seção Skills, Gates e Design System.

Features e Pull Requests guiados por SDD

Cada feature = 1 spec = 1 branch = 1 PR. O PR referencia a spec, e o revisor confere a implementação contra os critérios de aceite (não contra o "gosto"). PRs menores, revisão mais rápida, rastreabilidade de requisito → código → teste.

Testes E2E com Playwright e avaliação de critérios

Critérios de aceite em Given/When/Then mapeiam quase 1:1 para testes E2E. O agente pode usar o Playwright (inclusive via MCP) para navegar na aplicação como um usuário e verificar o comportamento.

Exemplo: critério de aceite → teste Playwright

// Critério: Dado um pedido PAGO criado há 2h, quando o usuário cancela,
// então vê "Pedido cancelado" e o status muda para CANCELADO.
import { test, expect } from "@playwright/test";

test("cancela pedido pago dentro de 24h", async ({ page }) => {
  await page.goto("/pedidos/42");
  await page.getByRole("button", { name: "Cancelar pedido" }).click();
  await page.getByLabel("Motivo").selectOption("desisti");
  await page.getByRole("button", { name: "Confirmar" }).click();
  await expect(page.getByText("Pedido cancelado")).toBeVisible();
  await expect(page.getByTestId("status")).toHaveText("CANCELADO");
});

Desenvolvimento Paralelo com SDD

🎯 Objetivo

Rodar várias features/tarefas ao mesmo tempo com subagentes ou sessões paralelas, sem que se atrapalhem.

🧩 Para que serve

Reduzir o tempo total de entrega e economizar contexto: um orquestrador coordena, workers executam com contexto próprio.

✅ Quando usar

Quando o plano tem tarefas independentes (módulos diferentes, poucos arquivos em comum) e o projeto tem gates automáticos confiáveis.

⛔ Quando evitar / cuidados

Tarefas que mexem nos mesmos arquivos geram conflitos; paralelizar sem testes automatizados multiplica bugs e a carga de revisão.

Integração entre features e regras de ouro

Desenvolver várias features em paralelo (com vários agentes) só funciona se elas não colidirem. Regras de ouro:

  1. Contratos primeiro: defina interfaces/APIs compartilhadas antes de paralelizar.
  2. Isolamento físico: cada agente em seu próprio git worktree/branch.
  3. Baixa sobreposição de arquivos: planeje para que features toquem áreas diferentes.
  4. Integração contínua: merges pequenos e frequentes; testes de integração rodando no merge.
  5. Um dono por arquivo compartilhado (ex.: rotas, migrações) ou serialização dessas mudanças.

Geração de features em batch com subagentes

Um subagente é um agente com contexto próprio, instruções próprias e ferramentas limitadas, chamado por um agente principal. Ele faz o trabalho "sujo" (ler muitos arquivos, implementar uma task) e devolve só um resumo, preservando o contexto do principal.

Exemplo: subagente implementador (Claude Code)

<!-- .claude/agents/implementer.md -->
---
name: implementer
description: Implementa UMA task do plano seguindo a spec. Use para tasks independentes.
tools: Read, Edit, Write, Bash, Grep, Glob
---
Você implementa exatamente uma task de docs/plan.md.
1. Leia a spec referenciada e os arquivos citados na task.
2. Escreva o teste primeiro; depois a implementação mínima.
3. Rode os testes do módulo até passarem. Não altere testes de outras tasks.
4. Responda com: arquivos alterados, testes executados, pendências.

Ver Subagents na documentação do Claude Code.

Arquitetura de orquestrador para economia de tokens

┌──────────── ORQUESTRADOR (contexto enxuto) ────────────┐ │ lê plan.md, despacha tasks, recebe RESUMOS, atualiza estado │ └───────┬──────────────────┬──────────────────┬───────────┘ ▼ ▼ ▼ subagente T1 subagente T2 subagente T3 (lê 40 arquivos) (lê 25 arquivos) (roda testes E2E) └─── devolve 10 linhas ───┴──────────┘

O orquestrador nunca lê o código inteiro: só o plano e os resumos. Os subagentes podem usar modelos mais baratos para tarefas simples. Resultado: o contexto principal não estoura e o custo cai.

Execução de agentes em paralelo e resolução de conflitos

  • Use git worktree para ter várias cópias de trabalho do mesmo repositório, uma por agente.
  • Conflitos de merge: resolva com o agente lendo as duas specs (intenção de cada lado), não só o diff.
  • Conflitos semânticos (compila, mas quebra comportamento): só testes de integração pegam — rode-os após cada merge.

Exemplo: worktrees para agentes paralelos

git worktree add ../app-feat-cancel -b feat/cancelamento
git worktree add ../app-feat-export -b feat/exportacao-csv

# em cada pasta, uma sessão de agente independente
cd ../app-feat-cancel && claude
cd ../app-feat-export && claude

git worktree list
git worktree remove ../app-feat-cancel   # depois do merge

Harness Engineering

🎯 Objetivo

Entender o harness — tudo em volta do modelo (loop, ferramentas, contexto, permissões, hooks, verificação) — e como construir o seu.

🧩 Para que serve

Transformar um agente genérico num agente confiável para o seu projeto, com limites claros e verificação externa.

✅ Quando usar

Quando você usa agentes todos os dias no mesmo repositório e percebe erros repetidos: declarar pronto sem testar, desviar da spec, ações perigosas.

⛔ Quando evitar / cuidados

Não tente resolver tudo só com prompt ("por favor, sempre rode os testes"): o que é crítico deve ser garantido mecanicamente (hooks, gates, permissões).

O que é Agent Harness (general-purpose e user harness)

O harness é tudo ao redor do modelo que o transforma em agente: o loop, as ferramentas, o gerenciamento de contexto, permissões, hooks, subagentes, memória, verificação. "Modelo + harness = agente".

  • General-purpose harness: o que vem pronto na ferramenta (Claude Code, Cursor agent, Claude Agent SDK) — loop, ferramentas de arquivo/terminal, compactação.
  • User harness: o que você constrói em cima para o seu projeto: CLAUDE.md/AGENTS.md, skills, comandos, subagentes, hooks, scripts de inicialização, gates de qualidade, arquivos de estado.

Harness × Context × Prompt Engineering

DisciplinaPergunta que respondeArtefatos
Prompt engineeringComo formular esta instrução?Prompts, templates
Context engineeringQuais tokens o modelo vê a cada passo?Memória, RAG, compactação, resultados de ferramentas
Harness engineeringQual o ambiente, as ferramentas, os limites e os ciclos de verificação do agente?Skills, hooks, gates, subagentes, scripts, estado

Context anxiety e self-evaluation

  • Context anxiety: à medida que a janela de contexto enche, modelos tendem a apressar o fim — resumir demais, pular verificações, declarar "concluído". Mitigação: tarefas menores, sessões novas por task com estado em arquivos, compactação, subagentes.
  • Self-evaluation: agentes tendem a avaliar o próprio trabalho de forma otimista. Mitigação: verificação externa (testes, um subagente avaliador com rubrica e sem acesso ao raciocínio do implementador, verificação funcional no navegador).

Desafios para domar o agente

  • Tentar fazer tudo de uma vez ("one-shot") e se perder.
  • Declarar vitória sem testar de ponta a ponta.
  • Deixar o ambiente quebrado entre sessões.
  • Desviar da spec ("melhorias" não pedidas).
  • Ações destrutivas (apagar arquivos, git reset --hard, migrações em produção).
O artigo Effective harnesses for long-running agents (Anthropic) mostra um harness com agente inicializador (cria lista de features, init.sh, arquivo de progresso e commit inicial) + agente de código que, em cada sessão, faz uma feature, testa de ponta a ponta, commita e atualiza o progresso.

Exemplo: um guardrail mecânico com hook do Claude Code

Em vez de pedir "não rode comandos destrutivos", o hook bloqueia antes da execução:

// .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [{ "type": "command", "command": ".claude/hooks/bloquear-perigosos.sh" }]
      }
    ]
  }
}
#!/usr/bin/env bash
# .claude/hooks/bloquear-perigosos.sh — recebe o JSON da chamada pelo stdin
cmd=$(jq -r '.tool_input.command')
if echo "$cmd" | grep -Eq 'rm -rf|git reset --hard|git push --force|DROP TABLE'; then
  echo "Comando bloqueado pelo harness: $cmd" >&2
  exit 2   # código 2 = bloqueia e devolve a mensagem ao agente
fi

Veja Hooks reference. O mesmo mecanismo serve para rodar o formatter após cada edição ou os testes antes de encerrar.

Princípios de Harness Engineering

🎯 Objetivo

Conhecer os princípios de harness engineering: subagentes, artefatos e estado, unidades pequenas e verificáveis, guardrails mecânicos e avaliação por rubrica.

🧩 Para que serve

Ter um checklist para desenhar e revisar o harness de qualquer projeto.

✅ Quando usar

Ao montar o harness do zero ou quando o agente começa a falhar em tarefas longas.

⛔ Quando evitar / cuidados

Excesso de regras e gates lentos frustram o fluxo: cada gate deve ser rápido e checar algo que realmente quebra.

Orquestração de subagentes

Especialize: explorer (só leitura, mapeia código), implementer, tester, reviewer. O orquestrador decide quem chamar, em que ordem, e consolida.

Artefatos, estado e unidades pequenas e verificáveis

Exemplo: lista de features como estado (JSON)

[
  { "id": "F-01", "descricao": "Usuário cancela pedido PAGO < 24h",
    "passos_verificacao": ["abrir /pedidos/42", "clicar Cancelar", "ver status CANCELADO"],
    "passa": false },
  { "id": "F-02", "descricao": "Botão oculto para pedido ENVIADO",
    "passos_verificacao": ["abrir /pedidos/43", "botão ausente"],
    "passa": true }
]

Regra para o agente: só pode mudar passa para true após verificar; nunca remover ou editar descrições.

Guardrails e enforcements mecânicos

Instrução no prompt é sugestão; enforcement mecânico é garantia. Use permissões (allow/deny de comandos), hooks e CI.

Exemplo: hooks e permissões no Claude Code (.claude/settings.json)

{
  "permissions": {
    "deny": ["Bash(git push:*)", "Bash(rm -rf:*)", "Read(./.env)"]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npm run lint --silent" }]
      }
    ]
  }
}

Ver Hooks guide, Hooks reference e Settings.

Evaluation, rubrics e verificação funcional

  • Rubrica: lista objetiva de critérios ("todos os RFs têm teste", "nenhum any novo", "sem console.log").
  • Verificação funcional: rodar a aplicação e testar como usuário (Playwright, curl), não só testes unitários.
  • Avaliador separado: subagente que recebe spec + diff + rubrica e dá parecer.

Observabilidade e gestão de degradação

Monitore o agente: tokens por task, número de iterações, taxa de testes quebrados, tempo. Sinais de degradação (loops, repetição, edições que desfazem edições) → interrompa, compacte ou reinicie com o estado salvo. Ver custos e monitoramento de uso no Claude Code.

Skills, Gates e Design System

🎯 Objetivo

Criar skills (SKILL.md com instruções, scripts e exemplos), scaffolding, AGENTS.md, gates de qualidade e guidelines de UI/design system.

🧩 Para que serve

Empacotar conhecimento do projeto que o agente carrega só quando precisa, e impedir mecanicamente que código fora do padrão avance.

✅ Quando usar

Skills: procedimentos recorrentes (criar migração, gerar componente). Gates: lint, tipos, testes, build e checagens específicas antes de commit/PR.

⛔ Quando evitar / cuidados

Skill com instruções genéricas não agrega. Gate que falha aleatoriamente (teste flaky) ensina o agente — e o time — a ignorá-lo.

Criação de Skills para Harness Engineering (SKILL.md)

Uma skill é uma pasta com um SKILL.md (frontmatter com name e description + instruções) e, opcionalmente, scripts, templates e referências. Só o nome e a descrição ficam sempre no contexto; o conteúdo completo é carregado quando a tarefa pede — progressive disclosure.

Exemplo: skill spec-writer

.claude/skills/spec-writer/
├── SKILL.md
├── templates/spec.md
└── scripts/check_spec.py      # valida se todos os RFs têm critério de aceite
---
name: spec-writer
description: Gera especificação técnica a partir de um PRD. Use quando o usuário pedir spec, especificação ou plano a partir de docs/prd/*.md.
---
# Spec Writer
1. Leia o PRD indicado e explore o código relacionado (somente leitura).
2. Preencha templates/spec.md: comportamento, contratos, dados, erros, critérios.
3. Toda ambiguidade vira item em "Perguntas em aberto" — não invente.
4. Rode `python scripts/check_spec.py <arquivo>` e corrija até passar.
5. Salve em docs/specs/<feature>.md e mostre o resumo.

Ver Claude Code Skills, Agent Skills overview e o repositório anthropics/skills.

Scaffolding, scripts e AGENTS.md

Scripts determinísticos fazem melhor (e mais barato) o que é repetitivo: gerar a estrutura de um módulo, criar migração com timestamp, popular o banco de dev. O agente apenas os chama. AGENTS.md é o arquivo de instruções aberto lido por várias ferramentas (equivalente ao CLAUDE.md).

Gates do projeto e scripts de inicialização

Gates são verificações obrigatórias que bloqueiam o avanço: lint, tipos, testes, build, cobertura mínima, E2E. Um único comando (make check) facilita para o agente e para o CI. O script de inicialização (init.sh) sobe o ambiente do zero e faz um smoke test — o agente roda no início de cada sessão para garantir que parte de um estado saudável.

Exemplo: init.sh + gate

#!/usr/bin/env bash
set -euo pipefail
docker compose up -d db
npm ci --silent
npm run db:migrate
npm run dev &          # sobe a aplicação
npx wait-on http://localhost:3000/health
echo "Ambiente OK"

# Makefile
# check: ; npm run lint && npm run typecheck && npm test && npm run e2e

Guidelines de UI, tokens e Design System

Sem guidelines, cada tela gerada pela IA terá cores, espaçamentos e componentes diferentes. Forneça: os design tokens (cores, tipografia, espaçamentos como variáveis), a biblioteca de componentes a usar (ex.: shadcn/ui) e regras ("nunca use cores hex diretamente; use tokens"). Detalhes na Disciplina 07.

Ciclo Completo de Implementação

🎯 Objetivo

Ver o fluxo de ponta a ponta: PRD writer → spec writer → contrato → implementação → avaliação → tracking.

🧩 Para que serve

Ter um processo repetível em que cada etapa produz um artefato revisável e o resultado final é comparado com o que foi combinado.

✅ Quando usar

Ao implementar features completas com agentes e quando várias pessoas/agentes precisam acompanhar o progresso.

⛔ Quando evitar / cuidados

Não pule a avaliação contra o contrato: é ali que se descobre o que o agente "esqueceu" ou fez a mais.

PRD Writer, tracking e SpecWriter na prática

  1. /prd-writer entrevista você e gera docs/prd/feature.md.
  2. /spec-writer gera a spec e o plano de tasks.
  3. Tracking: tasks num arquivo (ou issues) com status; o agente atualiza a cada conclusão.

Contract.md e avaliação de arquivos gerados

Um contrato define, antes da implementação, o que será entregue: arquivos que serão criados/alterados, interfaces públicas, comandos de verificação e critérios. Depois, um avaliador compara o entregue com o contrato.

Exemplo: contract.md

# Contrato — T3 CancelarPedido
## Arquivos
- CRIAR src/orders/app/cancel-order.usecase.ts
- CRIAR src/orders/app/cancel-order.usecase.spec.ts
- ALTERAR src/orders/domain/order.ts (apenas método cancel)
- NÃO ALTERAR nada fora de src/orders/
## Interface
execute(orderId: string, reason: CancelReason): Promise<Result<Order, CancelError>>
## Verificação
- `npm test -- cancel-order` passa
- cobertura do arquivo ≥ 90%
## Critérios de aceite cobertos
RF-01, RF-03

Ciclo completo de implementação e workflow

PRD → Spec → Plano/Tasks → (por task) Contrato → Teste falhando → Implementação → Gates (lint, tipos, testes) → Verificação funcional → Avaliador (rubrica) → Commit + atualização do estado → próxima task → PR → Review humano → Merge

Avaliação e análise pós-implementação

Retrospectiva com dados: quantas iterações por task, onde o agente errou, quais instruções faltavam. Transforme cada erro recorrente em melhoria do harness (nova rule, novo gate, ajuste de skill). É assim que o "5x" aparece: o harness melhora a cada ciclo.

Paralelização e tmux

🎯 Objetivo

Organizar a execução paralela em waves (ondas) e operar várias sessões de agente com tmux e git worktrees.

🧩 Para que serve

Acompanhar vários agentes num só terminal, sem perder sessões ao desconectar, e consolidar resultados de forma ordenada.

✅ Quando usar

Quando você já tem tarefas independentes e quer rodar 2–4 agentes ao mesmo tempo, cada um no seu worktree.

⛔ Quando evitar / cuidados

Não comece com 8 agentes: a revisão vira gargalo. E nunca rode dois agentes no mesmo diretório de trabalho — use worktrees.

Skill para paralelização independente

Uma skill pode analisar o plano, montar o grafo de dependências e identificar quais tasks podem rodar em paralelo sem conflito (sem dependência entre si e com baixa sobreposição de arquivos).

Waves e consolidação de resultados

Wave 1 (paralelo): T1 migração | T2 domínio | T6 tela de listagem
       → merge + gates
Wave 2 (paralelo): T3 caso de uso | T7 exportação CSV
       → merge + gates
Wave 3: T4 endpoint → T5 UI → E2E completo

Ao fim de cada wave: merge, rodar todos os gates, resolver conflitos, atualizar o estado — só então inicia a próxima.

Multi-sessão na prática com tmux

tmux é um multiplexador de terminal: várias sessões/painéis num terminal só, que continuam rodando se você desconectar.

Exemplo: um painel por agente

# cria sessão com 3 painéis, cada um num worktree diferente
tmux new-session -d -s agentes -c ../app-feat-cancel
tmux split-window -h -t agentes -c ../app-feat-export
tmux split-window -v -t agentes -c ../app-feat-list
tmux send-keys -t agentes:0.0 'claude' C-m
tmux send-keys -t agentes:0.1 'claude' C-m
tmux send-keys -t agentes:0.2 'claude' C-m
tmux attach -t agentes

# atalhos (prefixo Ctrl+b): setas = trocar painel · d = desanexar · z = zoom no painel
Paralelizar multiplica também o custo e a carga de revisão. Comece com 2 agentes; aumente quando o harness (gates, contratos) estiver maduro.

Exemplo: um worktree por agente

# cada feature num diretório e branch separados, mesmo repositório
git worktree add ../app-filtro-data   -b feat/filtro-data
git worktree add ../app-export-csv    -b feat/export-csv

tmux new-session -d -s agentes -c ../app-filtro-data 'claude'
tmux split-window -h -t agentes -c ../app-export-csv 'claude'
tmux attach -t agentes          # Ctrl-b + setas para trocar de painel

Exercícios e quiz

Exercício — seu primeiro harness
  1. Crie as skills prd-writer e spec-writer.
  2. Crie init.sh, make check e um hook que roda lint após edições.
  3. Crie os subagentes implementer e reviewer.
  4. Implemente uma feature com 4+ tasks em 2 waves usando worktrees e tmux.
  5. Faça a retrospectiva e registre 3 melhorias no harness.
1. O agente declara "tudo pronto", mas a feature não funciona no navegador. Melhor correção no harness?
Enforcement mecânico e verificação externa vencem instruções genéricas.
2. Por que subagentes economizam tokens no orquestrador?
O contexto "pesado" fica no subagente; o principal recebe só o essencial.
3. No nível "spec-as-source" do SDD…
É o nível mais radical: edita-se a spec, regenera-se o código.
