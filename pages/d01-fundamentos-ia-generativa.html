Disciplina 01

Fundamentos de IA Generativa

IA não é mais coisa só para cientistas de dados. Entender como um LLM funciona é o que separa quem usa IA de quem constrói com IA.

Ao finalizar esta disciplina você será capaz de:

  • Construir uma base sólida sobre IA generativa
  • Entender como diferentes modelos impactam suas ferramentas
  • Avaliar limitações e possibilidades antes de usar uma IA
  • Comparar e testar modelos no seu próprio ambiente
  • Navegar com clareza pelo ecossistema de GenAI

Introdução à IA Generativa

🎯 Objetivo

Situar a IA generativa na história da IA e entender o que muda quando o computador passa a produzir conteúdo em vez de só classificar.

🧩 Para que serve

Dar vocabulário e critério para conversar sobre IA com produto, gestão e outros devs, e reconhecer que tipo de IA resolve cada problema.

✅ Quando usar

Ao avaliar se um problema pede regras fixas, um modelo estatístico clássico ou um LLM (ex.: "precisamos de um chatbot ou de um formulário com regras?").

⛔ Quando evitar / cuidados

Não use IA generativa onde uma regra determinística resolve (cálculo de imposto, validação de CPF): é mais cara, mais lenta e pode errar.

Conceitos e evolução histórica dos modelos generativos

IA generativa é o ramo da IA que cria conteúdo novo — texto, código, imagens, áudio — aprendendo a distribuição estatística dos dados de treinamento. Em vez de apenas classificar ("isto é spam?"), o modelo produz ("escreva uma resposta a este e-mail").

1990–2000sAprendizado estatístico (n-gramas, SVM, HMM)Modelos aprendem padrões dos dados; modelos de linguagem por contagem de palavras.
2013Word2VecPalavras viram vetores; "rei − homem + mulher ≈ rainha". Nascem os embeddings.
2014GANs, Seq2Seq com RNN/LSTMPrimeiras gerações convincentes de imagens e tradução neural.

Na prática: sistemas reais combinam os três. Uma regra de negócio valida a saída do LLM; um classificador estatístico decide se a pergunta vai para o LLM ou para uma FAQ.

Principais impactos no desenvolvimento de software e produtos

  • Produtividade do dev: geração de código, testes, documentação, refatoração e revisão assistidas.
  • Novas features: busca semântica, sumarização, extração de dados de documentos, atendimento, copilotos internos.
  • Novos requisitos não funcionais: custo por token, latência, não determinismo, avaliação contínua (evals), segurança contra prompt injection.
  • Novo papel do dev: menos digitação, mais especificação, revisão e orquestração.

Modelos de Linguagem (LLMs)

🎯 Objetivo

Entender o que é um LLM, como ele aprende, quais famílias existem (proprietários, open source, multimodais) e como executá-los localmente.

🧩 Para que serve

Escolher o modelo certo para cada caso: grande e capaz para raciocínio difícil; pequeno e barato para tarefas simples em alto volume; local quando os dados não podem sair da empresa.

✅ Quando usar
  • Modelo de ponta via API: agentes, código, análise complexa.
  • Modelo pequeno/rápido: classificação, extração, roteamento.
  • Open source local (Ollama, Hugging Face): dados sensíveis, uso offline, custo fixo.
⛔ Quando evitar / cuidados

Rodar modelo local "para economizar" sem medir: GPUs, manutenção e qualidade inferior costumam custar mais que a API em volumes baixos.

O que são LLMs e como aprendem a gerar conteúdo

Um Large Language Model é uma rede neural (quase sempre um Transformer) com bilhões de parâmetros, treinada para uma tarefa aparentemente simples: prever o próximo token dado o texto anterior. Para acertar essa previsão em trilhões de exemplos (livros, código, web), o modelo precisa internalizar gramática, fatos, padrões de raciocínio e estilos de código.

Exemplo: a intuição de "prever o próximo token"

Entrada:  "A capital da França é"
Modelo calcula uma distribuição de probabilidade sobre o vocabulário:
   " Paris"   0.92
   " a"       0.03
   " uma"     0.01
   ...
Escolhe um token (amostragem), anexa ao texto e repete o processo.

Depois do pré-treinamento, o modelo passa por ajuste de instruções (exemplos de pergunta → boa resposta) e por aprendizado por reforço com feedback (humano ou de IA, como a Constitutional AI da Anthropic) para virar um assistente útil, honesto e seguro.

Generalistas × especializados × multimodais

  • Generalistas: fazem de tudo razoavelmente bem (Claude, GPT, Gemini). Ótimos como ponto de partida.
  • Especializados: treinados ou ajustados para um domínio (código, medicina, jurídico) ou tamanho reduzido para rodar barato/local. Ex.: modelos de código, modelos de embeddings, modelos pequenos para classificação.
  • Multimodais: aceitam (e às vezes geram) mais de uma modalidade — texto + imagem + PDF + áudio. O Claude, por exemplo, lê imagens e PDFs nativamente (Vision, PDF support).
Regra prática para escolher: comece com o modelo mais capaz para validar que a tarefa é possível; depois meça se um modelo menor/mais barato mantém a qualidade. A doc Choosing a model descreve esse trade-off entre capacidade, velocidade e custo.

Modelos open source: LLaMA, DeepSeek, Hugging Face

  • LLaMA (Meta): família de modelos com pesos abertos (com licença própria) que popularizou o ecossistema open weights.
  • DeepSeek: modelos chineses de pesos abertos, notáveis por eficiência (Mixture of Experts) e por modelos de raciocínio.
  • Hugging Face: não é um modelo, é o "GitHub dos modelos": hub com centenas de milhares de modelos, datasets, a biblioteca transformers e leaderboards.

Vantagens: privacidade (os dados não saem da sua infra), custo previsível, possibilidade de fine-tuning. Desvantagens: você opera a infraestrutura (GPU), e os melhores modelos proprietários ainda costumam liderar em tarefas complexas e agênticas.

Execução local: Ollama, LM Studio e alternativas

  • Ollama — CLI + servidor HTTP local; ollama run llama3.2 baixa e roda. Ideal para devs.
  • LM Studio — app desktop com interface gráfica e servidor compatível com a API da OpenAI.
  • Alternativas: llama.cpp (motor C++ usado por baixo por vários deles), vLLM (servir em produção com alto throughput), GPT4All, Jan.

Exemplo: rodando e chamando um modelo local com Ollama

# instalar (Linux/WSL)
curl -fsSL https://ollama.com/install.sh | sh

# baixar e conversar
ollama run llama3.2

# chamar via HTTP (porta padrão 11434)
curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "Explique o que é um token em uma frase.",
  "stream": false
}'
Quantização: modelos locais costumam vir "quantizados" (pesos em 4 ou 8 bits em vez de 16). Ocupam bem menos memória com pequena perda de qualidade. Um modelo de 8B parâmetros em 4 bits roda em ~5–6 GB de RAM/VRAM.

Geração de Respostas

🎯 Objetivo

Entender como uma resposta é gerada token a token e como tokens, temperatura, top-p e janela de contexto afetam qualidade, custo e latência.

🧩 Para que serve

Estimar custo (cobra-se por token), ajustar a criatividade/determinismo da saída e evitar estourar o limite de contexto.

✅ Quando usar

Sempre que configurar uma chamada à API: max_tokens e o tamanho do contexto entram em todo projeto; temperatura importa ao alternar entre tarefas criativas e tarefas exatas.

⛔ Quando evitar / cuidados

Não use temperatura alta para extração de dados ou código (aumenta variação e erro). E não ajuste temperatura e top-p ao mesmo tempo — mexa em um só.

Tokens e tokenização

LLMs não leem letras nem palavras: leem tokens, pedaços de texto definidos por um algoritmo como BPE (Byte Pair Encoding). Palavras comuns viram 1 token; palavras raras são quebradas em vários. Em inglês, 1 token ≈ 4 caracteres; em português costuma haver um pouco mais de tokens por palavra.

"desenvolvimento" → ["des", "envol", "vimento"]   (ilustrativo)
"Hello world"     → ["Hello", " world"]

Por que importa: preço, limite de contexto e latência são medidos em tokens. Cada modelo tem seu tokenizador — a mesma frase pode custar quantidades diferentes de tokens em modelos diferentes.

Exemplo: contando tokens com a API do Claude (Python)

import anthropic

client = anthropic.Anthropic()  # lê ANTHROPIC_API_KEY do ambiente

count = client.messages.count_tokens(
    model="claude-opus-5-5",
    messages=[{"role": "user", "content": "Explique tokenização para um dev júnior."}],
)
print(count.input_tokens)

Processo de inferência e fluxo de geração

  1. Tokenização do prompt.
  2. Prefill: o modelo processa todos os tokens de entrada em paralelo e monta o KV cache (memória interna da atenção). Esta etapa domina o "tempo até o primeiro token" (TTFT).
  3. Decode: gera um token por vez; cada novo token é anexado e o passo se repete. Domina o tempo total em respostas longas.
  4. Parada: ao gerar um token de fim, atingir max_tokens ou uma sequência de parada.
  5. Destokenização e, opcionalmente, streaming dos tokens para o cliente conforme saem.

Parâmetros de geração: temperatura, top-k e top-p

Na etapa de escolha do próximo token, o modelo tem uma distribuição de probabilidades. Os parâmetros de sampling controlam como escolhemos:

ParâmetroO que fazEfeito
temperature"Achata" (alta) ou "afia" (baixa) a distribuição.0 ≈ quase determinístico; 1 = padrão; alto = mais criativo/aleatório.
top-kConsidera só os k tokens mais prováveis.k=1 é greedy decoding.
top-p (nucleus)Considera o menor conjunto de tokens cuja probabilidade somada ≥ p.p=0.9 corta a "cauda" improvável, adaptando-se ao contexto.

Exemplo: ajustando sampling num modelo local (Ollama)

curl http://localhost:11434/api/generate -d '{
  "model": "llama3.2",
  "prompt": "Sugira 5 nomes para uma API de pagamentos.",
  "stream": false,
  "options": { "temperature": 1.1, "top_k": 40, "top_p": 0.9 }
}'
Atenção — APIs modernas mudaram: nos modelos Claude mais recentes, os parâmetros temperature, top_p e top_k foram removidos da API (enviar retorna erro 400). A "dose" de raciocínio e esforço passou a ser controlada pelo parâmetro effort e pelo adaptive thinking. O conceito de sampling continua essencial para entender modelos locais e outros provedores.

Janela de contexto (context window) e truncamento

A janela de contexto é o número máximo de tokens que o modelo enxerga de uma vez: system prompt + histórico + documentos + ferramentas + a resposta que está sendo gerada. Modelos atuais do Claude chegam a 1M de tokens (Context windows).

  • Truncamento: quando o conteúdo excede a janela, algo precisa sair. Estratégias: descartar as mensagens mais antigas (sliding window), resumir o histórico (sumarização / compaction), ou recuperar só os trechos relevantes (RAG).
  • Mais contexto ≠ melhor: contexto enorme custa mais, aumenta latência e pode diluir a atenção do modelo ("context rot"). Contexto é um recurso finito — trate-o como tal (ver Effective context engineering).

Arquiteturas e Tipos de Modelos

🎯 Objetivo

Distinguir encoder-only, decoder-only e encoder-decoder, e os tipos de modelo (texto, código, embeddings, multimodal).

🧩 Para que serve

Escolher a ferramenta certa: modelos de embeddings para comparar/buscar, decoders (LLMs) para gerar/raciocinar.

✅ Quando usar

Ao desenhar uma feature: busca semântica e detecção de duplicatas → embeddings; resumo, chat, código → LLM generativo; ler imagem/PDF → multimodal.

⛔ Quando evitar / cuidados

Não use um LLM generativo para calcular similaridade entre milhões de documentos — é ordens de grandeza mais caro e lento do que embeddings.

Encoder-only, decoder-only e encoder-decoder

Modelos de texto, código, embeddings e multimodais

  • Texto: conversação, escrita, análise.
  • Código: treinados com ênfase em repositórios; bons em completar, explicar e corrigir código. Os modelos generalistas de ponta hoje são também excelentes em código.
  • Embeddings: não geram texto; transformam texto em vetor numérico. Base de busca semântica e RAG.
  • Multimodais: combinam visão, texto e às vezes áudio.

Comparação entre os estilos e seus usos ideais

Pergunta-guia: preciso gerar algo ou só entender/comparar? Para comparar e buscar, use embeddings (baratos e rápidos). Para gerar ou raciocinar, use um decoder. Para pipelines de alto volume e tarefa estreita (ex.: classificar tickets), um modelo pequeno pode bastar.

Como os LLMs funcionam por dentro

🎯 Objetivo

Ter um modelo mental de como o Transformer funciona (atenção, camadas) e de como o modelo é treinado (pré-treino, fine-tuning, alinhamento).

🧩 Para que serve

Explicar comportamentos do dia a dia: por que o modelo erra fatos raros, por que a ordem do contexto importa, por que ele não "sabe" o que aconteceu depois do treino.

✅ Quando usar

Ao depurar respostas estranhas, ao decidir entre fine-tuning e prompt, e ao explicar limitações para stakeholders.

⛔ Quando evitar / cuidados

Não é preciso saber a matemática para usar bem um LLM. Não tente "programar" o modelo achando que ele executa lógica como um interpretador: ele prevê texto provável.

Redes neurais e a arquitetura Transformer

Uma rede neural é uma composição de camadas que multiplicam vetores por matrizes de pesos e aplicam funções não lineares. O Transformer organiza isso em blocos repetidos com duas peças principais:

  1. Self-attention: cada token "olha" para os outros tokens e decide quais são relevantes para entendê-lo. Em "o banco estava cheio de peixes", a atenção conecta "banco" a "peixes" (banco de rio, não financeiro).
  2. Feed-forward (MLP): processa cada posição individualmente; acredita-se que boa parte do "conhecimento factual" fica armazenada aqui.
Tokens → Embeddings + posição ↓ ┌─────────── bloco Transformer (×N) ───────────┐ │ Multi-Head Self-Attention → soma + norma │ │ Feed-Forward (MLP) → soma + norma │ └──────────────────────────────────────────────┘ ↓ Camada final → probabilidades do próximo token (softmax)

Etapas de treinamento: pré-treinamento e fine-tuning

  • Pré-treinamento: previsão do próximo token em trilhões de tokens. Caríssimo (milhares de GPUs por semanas/meses). Resultado: um "modelo base" que completa texto.
  • Fine-tuning supervisionado (SFT): exemplos curados de instrução → resposta ideal.
  • Alinhamento (RLHF/RLAIF, Constitutional AI): o modelo aprende preferências — ser útil, honesto e inofensivo.
  • Treino para raciocínio e agentes: reforço em tarefas verificáveis (matemática, código, uso de ferramentas).

Noções de como o modelo aprende a gerar respostas

Durante o treino, para cada posição o modelo compara sua previsão com o token real e calcula um erro (cross-entropy loss). O algoritmo de backpropagation ajusta levemente bilhões de pesos para reduzir esse erro. Repetido trilhões de vezes, emergem capacidades como traduzir, resumir e programar — sem que ninguém as tenha programado explicitamente.

Exemplo: o que essa teoria explica na prática

  • "Ele inventou uma função que não existe na biblioteca." O modelo aprendeu padrões de nomes de API; uma função plausível tem alta probabilidade mesmo sem existir. Solução: dar a documentação no contexto (Context7, RAG).
  • "Ele não conhece a versão nova do framework." O pré-treino tem data de corte. Conhecimento posterior só entra pelo contexto.
  • "Respondeu diferente com a mesma pergunta." A saída é amostrada de uma distribuição de probabilidades; com temperatura > 0 há variação.
  • "Ficou educado e recusou algo perigoso." Efeito do alinhamento (RLHF/Constitutional AI), não do pré-treino.

Embeddings e Representações Vetoriais

🎯 Objetivo

Entender embeddings como vetores que representam significado e como medir proximidade semântica (cosseno).

🧩 Para que serve

Construir busca semântica, recomendação, agrupamento de conteúdo, detecção de duplicatas e a etapa de recuperação de um RAG.

✅ Quando usar

Quando a busca por palavra-chave falha porque as pessoas usam palavras diferentes para a mesma coisa ("não consigo entrar" × "erro de login").

⛔ Quando evitar / cuidados

Busca por código exato, SKU, número de pedido ou nome próprio raro: embeddings vão mal. Combine com busca lexical (BM25) — a chamada busca híbrida.

Representações numéricas e proximidade semântica

Um embedding é um vetor (ex.: 1024 números) que representa o significado de um texto. Textos com significado parecido ficam próximos no espaço vetorial. A proximidade costuma ser medida por similaridade de cosseno:

cos(A, B) = (A · B) / (‖A‖ · ‖B‖)     → 1 = mesmo sentido, 0 = sem relação

Exemplo: busca semântica mínima com sentence-transformers

# pip install sentence-transformers
from sentence_transformers import SentenceTransformer, util

model = SentenceTransformer("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")

docs = [
    "Como redefinir minha senha?",
    "Política de reembolso para compras canceladas",
    "Configurar autenticação de dois fatores",
]
query = "esqueci a senha da conta"

doc_vecs = model.encode(docs, normalize_embeddings=True)
q_vec = model.encode(query, normalize_embeddings=True)

scores = util.cos_sim(q_vec, doc_vecs)[0]
best = scores.argmax().item()
print(docs[best], float(scores[best]))   # → "Como redefinir minha senha?"

Embeddings × geração

Embeddings representam; modelos generativos produzem. Num sistema RAG você usa os dois: embeddings para encontrar os trechos relevantes, e o LLM para redigir a resposta com base neles. O Claude não oferece um endpoint próprio de embeddings — a documentação de embeddings recomenda provedores especializados (como Voyage AI) e explica como escolher um modelo.

Casos de uso em busca, recomendação e organização de conteúdo

  • Busca semântica ("esqueci a senha" encontra "redefinir senha").
  • Recomendação (artigos/produtos parecidos com o que o usuário viu).
  • Clusterização e organização (agrupar tickets por assunto, detectar duplicatas).
  • Classificação leve (comparar com vetores "protótipo" de cada categoria).
  • Base do RAG (Disciplinas 03 e 07).

Alucinação em LLMs

🎯 Objetivo

Entender por que LLMs inventam informações com confiança e conhecer as estratégias para reduzir isso.

🧩 Para que serve

Projetar aplicações confiáveis: dar fontes ao modelo, permitir que ele diga "não sei", exigir citações e validar a saída.

✅ Quando usar

Em qualquer aplicação em que um erro factual cause dano: suporte ao cliente, jurídico, saúde, financeiro, geração de código que chama APIs.

⛔ Quando evitar / cuidados

Não confie em "o modelo é muito bom, não alucina": a taxa diminui, mas não zera. Também não peça fatos de nicho sem fornecer a fonte no contexto.

O que é alucinação e por que acontece

Alucinação é quando o modelo gera algo plausível mas falso: uma função de biblioteca que não existe, uma citação inventada, um número errado. Acontece porque o modelo é treinado para produzir a continuação mais provável, não para verificar a verdade; quando não "sabe", a resposta fluente e confiante ainda é estatisticamente provável.

Fatores que aumentam: perguntas sobre fatos raros ou recentes, contexto ausente, instruções que pressionam por uma resposta ("responda sempre"), cadeias longas sem verificação.

Estratégias para reduzir alucinações

  • Permita dizer "não sei" explicitamente no prompt.
  • Forneça a fonte (RAG, documentos no contexto) e peça para responder somente com base nela.
  • Peça citações literais dos trechos usados — e descarte afirmações sem citação. A API do Claude tem Citations nativo.
  • Verificação: testes automatizados para código, uma segunda chamada que checa a primeira, self-consistency.
  • Ferramentas: deixe o modelo consultar uma API/busca em vez de "lembrar".

Exemplo: prompt que reduz alucinação

Responda à pergunta usando SOMENTE o documento entre <documento>.
Primeiro, extraia em <citacoes> os trechos literais que sustentam a resposta.
Se o documento não contiver a informação, responda exatamente:
"Não encontrei essa informação no documento."

<documento>
{{CONTRATO}}
</documento>

Pergunta: {{PERGUNTA}}

Conhecimento em tempo real e limitações do modelo

Todo modelo tem uma data de corte de treinamento: ele não sabe de eventos ou versões de bibliotecas posteriores. Soluções: ferramentas de busca na web, RAG sobre documentação atualizada, servidores MCP como o Context7 (documentação de bibliotecas sempre atual — Disciplina 07). Outras limitações: aritmética longa sem ferramenta, contagem de caracteres, fatos muito de nicho, e o não determinismo (mesma pergunta, respostas diferentes).

Estratégias de Uso: Prompt Engineering, RAG e Fine-tuning

🎯 Objetivo

Saber escolher entre prompt engineering, RAG e fine-tuning (ou combiná-los) para adaptar um LLM ao seu problema.

🧩 Para que serve

Evitar o erro clássico de ir direto para fine-tuning quando um prompt melhor ou um RAG resolveria com uma fração do custo.

✅ Quando usar
  • Prompt: sempre o primeiro passo.
  • RAG: o modelo precisa de conhecimento privado ou que muda (manuais, políticas, tickets).
  • Fine-tuning: formato/estilo muito específico em altíssimo volume, depois de esgotar os anteriores.
⛔ Quando evitar / cuidados

Fine-tuning não é boa forma de "ensinar fatos" que mudam: o modelo não cita fonte, e a cada mudança você treina de novo.

Há três formas principais de adaptar um LLM ao seu problema. Use-as nesta ordem, da mais barata para a mais cara:

Prompt EngineeringRAGFine-tuning

Melhoria de RAG: o artigo Contextual Retrieval da Anthropic mostra como adicionar contexto a cada trecho antes de indexá-lo e combinar embeddings com BM25 reduz bastante as falhas de recuperação.

Exemplo de decisão: assistente interno de RH

  1. Prompt engineering: definimos tom, formato e regra "se não souber, encaminhe para rh@". Resolve o comportamento, mas o modelo não conhece a política de férias da empresa.
  2. RAG: indexamos o handbook, políticas e FAQ. Agora ele responde com base nos documentos e cita a fonte. Quando a política muda, basta reindexar o PDF.
  3. Fine-tuning? Não foi necessário. Só faria sentido se, com milhões de perguntas/mês, quiséssemos um modelo pequeno e barato imitando o formato do grande.
Regra de bolso: problema de comportamento → prompt; problema de conhecimento → RAG; problema de custo/escala com comportamento já definido → considere fine-tuning ou um modelo menor.

Exercício prático 1 — compare modelos no seu ambiente

Instale o Ollama, baixe dois modelos de tamanhos diferentes (ex.: llama3.2:1b e llama3.2) e faça a mesma pergunta técnica aos dois e a um modelo de ponta via API. Registre numa tabela: qualidade (1–5), latência, se alucinou. Isso é o embrião de uma eval (Disciplina 02).

Exercício prático 2 — mini RAG

Pegue 10 parágrafos do README de um projeto seu, gere embeddings, e para uma pergunta recupere os 3 trechos mais próximos e envie ao LLM com o prompt "responda somente com base nos trechos". Teste uma pergunta cuja resposta não está nos trechos: o modelo admitiu que não sabe?

Prever o próximo token em escala massiva é o que faz emergir as demais capacidades.
2. Você precisa que o assistente responda sobre a política interna de férias, que muda todo trimestre. Melhor estratégia?
Conhecimento privado e mutável → RAG: basta reindexar os documentos, e as citações permitem auditar a resposta.
