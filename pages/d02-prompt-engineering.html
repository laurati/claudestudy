Disciplina 02

Prompt Engineering

Seus prompts são básicos e você sabe disso. Aqui você aprende técnicas, estruturas, templates, versionamento e — principalmente — como medir se um prompt é bom.

Ao finalizar esta disciplina você será capaz de:

  • Ter até 5x mais produtividade
  • Gerar códigos de alta qualidade
  • Minimizar erros básicos cometidos pela IA
  • Criar assistentes para gerar docs de contexto para IA
  • Ter uma biblioteca de prompts para diferentes tipos de projetos

Fundamentos

A importância do Prompt Engineering no desenvolvimento

Um LLM é como um colega brilhante que acabou de chegar na empresa: sabe muito, mas não conhece seu projeto, suas convenções nem o que você considera "pronto". Prompt engineering é a disciplina de dar a esse colega as instruções, o contexto e os exemplos certos — e de iterar com base em testes.

O teste de ouro da documentação do Claude: se você mostrasse o prompt a um colega sem contexto, ele saberia exatamente o que fazer? Se não, o modelo também não saberá.

Exemplo: prompt genérico × prompt engenheirado

❌ "Crie testes para essa função."

✅ "Você vai escrever testes unitários em Go (testing + testify) para a função
   ParseInvoice em invoice.go.
   Contexto: a função é usada no fluxo de faturamento; entradas vêm de um CSV
   enviado por clientes e frequentemente têm campos vazios e datas em formatos
   diferentes.
   Requisitos:
   - use table-driven tests;
   - cubra caminho feliz, campos ausentes, datas inválidas e valores negativos;
   - não altere invoice.go; se encontrar um bug, descreva-o ao final.
   Formato: apenas o arquivo invoice_test.go completo."

Os princípios básicos (todos detalhados em Prompting best practices):

  • Seja claro e direto: diga o objetivo, o público, o formato e o critério de sucesso.
  • Explique o porquê: "não use reticências porque o texto será lido por um TTS" funciona melhor que "NUNCA use reticências".
  • Dê exemplos (few-shot) quando o formato importa.
  • Estruture com tags XML para separar instruções, contexto e dados.
  • Deixe o modelo pensar em tarefas complexas.

Técnicas de Prompt e Raciocínio Estruturado

Zero-shot e Few-shot Prompting

Zero-shot: só a instrução, sem exemplos. Funciona para tarefas comuns. Few-shot (ou multishot): incluir de 3 a 5 exemplos de entrada → saída. É a forma mais confiável de fixar formato, tom e casos de borda. Os exemplos devem ser relevantes, diversos (cobrindo casos difíceis) e claramente delimitados.

Exemplo: few-shot para classificar commits

Classifique a mensagem de commit em: feat, fix, refactor, docs, test, chore.

<exemplos>
<exemplo><entrada>corrige NPE ao salvar usuário sem e-mail</entrada><saida>fix</saida></exemplo>
<exemplo><entrada>extrai validação de CPF para pacote próprio</entrada><saida>refactor</saida></exemplo>
<exemplo><entrada>adiciona endpoint de exportação em CSV</entrada><saida>feat</saida></exemplo>
</exemplos>

<entrada>{{MENSAGEM}}</entrada>
Responda apenas com a categoria.

Role Prompting

Atribuir um papel no system prompt ("Você é um engenheiro de SRE sênior revisando um runbook") ajusta vocabulário, nível de profundidade e prioridades. Funciona melhor quando o papel vem acompanhado de contexto concreto (empresa, público, restrições), não só de um título.

Chain of Thought (CoT) e Self-consistency

CoT: pedir que o modelo raciocine passo a passo antes de responder melhora tarefas de lógica, matemática e análise (paper). Versões: "pense passo a passo" (básica), passos guiados ("primeiro identifique X, depois…"), ou estruturada com tags <raciocinio> e <resposta> para separar e poder descartar o raciocínio.

Self-consistency (paper): gerar várias cadeias de raciocínio independentes e escolher a resposta mais frequente (votação). Mais caro, porém mais robusto.

Modelos com "thinking": os modelos Claude atuais têm raciocínio interno (adaptive thinking) controlado pelo parâmetro effort. Nesses casos, você não precisa pedir "pense passo a passo" — mas guiar o que considerar continua útil.

Tree of Thought e Skeleton of Thought

  • Tree of Thought (ToT) (paper): o modelo explora vários "ramos" de solução, avalia cada um e expande os promissores (busca em árvore). Útil em problemas com muitas alternativas — por exemplo, escolher entre três arquiteturas.
  • Skeleton of Thought (SoT) (paper): primeiro gera um esqueleto (tópicos), depois expande cada tópico — em paralelo, reduzindo latência. Ótimo para documentos longos.

Exemplo: ToT "em um prompt" para decisão arquitetural

Problema: precisamos processar 2 mil webhooks/s de pagamentos com garantia de não perder eventos.
1. Proponha 3 abordagens distintas.
2. Para cada uma, avalie: confiabilidade, custo, complexidade operacional (nota 1–5 e justificativa).
3. Descarte a pior e aprofunde as duas restantes com riscos e mitigação.
4. Recomende uma e liste o que precisaria ser verdade para mudar de ideia.

ReAct (Reasoning + Acting)

ReAct (paper) intercala Pensamento → Ação (chamar ferramenta) → Observação (resultado) em loop até concluir. É o padrão conceitual por trás dos agentes modernos e do tool use do Claude.

Pensamento: preciso saber a versão do Postgres em produção.
Ação: run_sql("select version()")
Observação: PostgreSQL 15.4
Pensamento: o recurso MERGE existe desde a 15, posso usá-lo.
Resposta: ...

Prompt Chaining com LangChain

Prompt chaining é dividir uma tarefa complexa em uma sequência de prompts menores, onde a saída de um vira entrada do próximo (Chain complex prompts). Cada elo fica mais simples, testável e depurável.

Exemplo: cadeia "extrair requisitos → gerar casos de teste" com LangChain

# pip install langchain-anthropic langchain-core
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

llm = ChatAnthropic(model="claude-opus-5-5", max_tokens=4000)

extrair = ChatPromptTemplate.from_template(
    "Liste, em bullets, os requisitos funcionais da user story abaixo.\n\n{story}"
)
casos = ChatPromptTemplate.from_template(
    "Para cada requisito, escreva casos de teste no formato Given/When/Then.\n\n{requisitos}"
)

chain = (
    extrair | llm | StrOutputParser()
    | (lambda req: {"requisitos": req})
    | casos | llm | StrOutputParser()
)

print(chain.invoke({"story": "Como cliente, quero cancelar um pedido em até 24h..."}))

Janela de Contexto e Otimização

Context Window vs memória

O LLM é sem estado (stateless): a cada chamada você reenvia tudo o que ele precisa saber. A "memória" de um chat é só a aplicação reenviando o histórico. Já a memória de longo prazo é algo que você implementa fora do modelo: arquivos (como o CLAUDE.md do Claude Code), um banco de dados, um banco vetorial ou a memory tool, de onde se recupera o que for relevante para colocar na janela.

Custo e latência

  • Você paga por tokens de entrada e de saída (saída costuma custar ~5× mais).
  • Latência ≈ tempo de prefill (proporcional à entrada) + tempo de decode (proporcional à saída).
  • Alavancas: prompt menor e mais focado, cache, modelo menor para subtarefas, limitar o tamanho da saída, streaming para latência percebida. Ver Pricing e Reduce latency.

Truncamento, sumarização e sliding window

EstratégiaComoRisco
TruncamentoCorta o que excede (início ou meio)Perde informação importante silenciosamente
Sliding windowMantém só as últimas N mensagensEsquece decisões antigas
SumarizaçãoSubstitui o histórico antigo por um resumoResumo pode omitir detalhes; custa uma chamada
HíbridaResumo do antigo + janela recente + fatos fixosMais complexa, mas a mais usada em produção

A API do Claude oferece compaction (sumarização automática no servidor) e context editing (remove resultados antigos de ferramentas).

Prompt Caching

Se várias requisições começam com o mesmo prefixo (system prompt longo, documentação, exemplos), o provedor pode guardar o processamento desse prefixo. Leituras do cache custam uma fração do preço normal e reduzem a latência. A regra de ouro: conteúdo estável primeiro, conteúdo variável depois — qualquer byte diferente no prefixo invalida o cache dali em diante.

Exemplo: cache de um manual extenso no system prompt (Python)

import anthropic

client = anthropic.Anthropic()
manual = open("manual_api_interna.md").read()  # ~50 mil tokens, raramente muda

resp = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=2000,
    system=[
        {"type": "text", "text": "Você responde dúvidas sobre a API interna."},
        {"type": "text", "text": manual, "cache_control": {"type": "ephemeral"}},
    ],
    messages=[{"role": "user", "content": "Como paginar o endpoint /orders?"}],
)

# Na 2ª chamada com o mesmo prefixo, cache_read_input_tokens > 0
print(resp.usage.cache_creation_input_tokens, resp.usage.cache_read_input_tokens)
Invalidadores silenciosos: colocar data/hora no system prompt, serializar JSON com chaves em ordem aleatória, mudar a lista de ferramentas a cada requisição.

Batch Prompting

Dois sentidos: (1) agrupar vários itens num mesmo prompt ("classifique estes 20 tickets") para economizar overhead; (2) usar uma API de lotes assíncrona. A Message Batches API processa milhares de requisições em background com ~50% de desconto — perfeito para avaliações, migrações de dados e enriquecimento em massa, quando não há usuário esperando.

Exemplo: Message Batches API

tickets = {"t1": "App trava ao abrir", "t2": "Quero 2ª via do boleto"}

batch = client.messages.batches.create(requests=[
    {
        "custom_id": tid,
        "params": {
            "model": "claude-opus-5-5",
            "max_tokens": 50,
            "messages": [{"role": "user", "content": f"Categoria (bug/financeiro/outro): {txt}"}],
        },
    }
    for tid, txt in tickets.items()
])

# depois (poll até processing_status == "ended"):
for r in client.messages.batches.results(batch.id):
    if r.result.type == "succeeded":
        print(r.custom_id, r.result.message.content[0].text)  # resultados vêm fora de ordem: use custom_id

Estrutura básica de prompts

Modularização de prompts para funções específicas

Em vez de um "prompt-monstro" que faz tudo, crie prompts pequenos e com uma responsabilidade (assim como funções): classificar_intencao, extrair_entidades, redigir_resposta. Cada um pode ser testado, versionado, cacheado e trocado de modelo de forma independente.

Um prompt bem estruturado costuma ter estes blocos:

1. Papel / contexto da tarefa       (quem é, para quem, por quê)
2. Instruções e regras              (o que fazer, o que evitar e por quê)
3. Exemplos                         (<exemplos>)
4. Dados de entrada                 (<documento>, <codigo>, <pergunta>)
5. Formato de saída                 (JSON, markdown, tags)
6. Lembrete final da tarefa         (útil com contexto longo: pergunta no FIM)
Contexto longo: coloque documentos grandes no topo e a pergunta no final — isso melhora a qualidade (Long context tips).

Prompt templates dinâmicos (com variáveis de entrada)

Separe a parte fixa (instruções) da variável (dados do usuário) usando placeholders como {{VARIAVEL}}. Vantagens: consistência, reuso, cache do trecho fixo, e testes com datasets. Ver Prompt templates and variables.

Exemplo: template com Jinja2

from jinja2 import Template

REVIEW = Template("""Revise o diff abaixo seguindo o guia de estilo do time.
<guia>{{ guia }}</guia>
<diff linguagem="{{ linguagem }}">
{{ diff }}
</diff>
Liste problemas por severidade (alta/média/baixa) com arquivo:linha.""")

prompt = REVIEW.render(guia=open("STYLE.md").read(), linguagem="go", diff=diff_text)

Guidelines e trade-offs

  • Específico × flexível: regras rígidas demais tornam o modelo literal e quebradiço; vagas demais geram respostas genéricas. Explique a intenção.
  • Diga o que fazer, não só o que não fazer ("escreva em prosa corrida" > "não use bullets").
  • Prompts escritos para modelos antigos (MAIÚSCULAS, "CRITICAL!!!", ameaças) tendem a causar exagero em modelos atuais. Use tom normal.
  • Prefill: técnica antiga de começar a resposta do assistente (ex.: {). Nos modelos Claude atuais ela não é suportada — use structured outputs para garantir JSON.

Prompts para Agentes e Workflows

Estruturas de prompts para execução de agentes

O system prompt de um agente funciona como um "manual de operação". Estrutura recomendada:

<papel> Quem você é e qual o objetivo do agente </papel>
<ambiente> Onde você está, a que tem acesso, o que é irreversível </ambiente>
<ferramentas> Quando usar cada uma (e quando NÃO usar) </ferramentas>
<processo> Planeje → execute em passos pequenos → verifique → reporte </processo>
<limites> Peça confirmação antes de: deletar, publicar, gastar dinheiro </limites>
<criterio_de_pronto> Testes passando, lint limpo, resumo das mudanças </criterio_de_pronto>

Também é prompt engineering a descrição das ferramentas: nomes claros, descrição do que fazem, parâmetros com exemplos e mensagens de erro úteis (Writing effective tools for agents).

Prompts para análise de arquiteturas e componentes

Com base no código e nos diagramas fornecidos:
1. Gere um diagrama C4 de containers em Mermaid.
2. Para cada componente: responsabilidade, dependências de entrada/saída.
3. Identifique acoplamentos problemáticos (ciclos, componentes "Deus").
4. Avalie aderência aos atributos de qualidade: {{ATRIBUTOS}}.
Diferencie FATOS observados no código de SUPOSIÇÕES.

Workflow Specification e orquestração

Para fluxos com várias etapas, especifique o workflow de forma declarativa — etapas, entradas/saídas, condições de transição, critérios de verificação — e deixe o código (ou um orquestrador) executar. Padrões de orquestração descritos em Building effective agents: prompt chaining, routing, parallelization, orchestrator-workers e evaluator-optimizer.

Exemplo: especificação de workflow em YAML

workflow: triagem_de_incidente
steps:
  - id: classificar
    prompt: prompts/classificar_alerta@v3
    output: {severidade: [sev1, sev2, sev3], servico: string}
  - id: coletar
    when: "classificar.severidade in ['sev1','sev2']"
    tools: [buscar_logs, buscar_metricas]
  - id: resumir
    prompt: prompts/resumo_incidente@v2
    verify: "contém hipótese, impacto e próximo passo"
  - id: notificar
    requires_human_approval: true

Gestão e Versionamento de Prompts

Versionamento e controle de versão em equipe

Prompts são código: mudam o comportamento do sistema e precisam de revisão, histórico e rollback. Guarde-os no Git, versione semanticamente (mudança de formato de saída = major) e associe cada versão aos resultados de avaliação.

Documentação e categorização

Cada prompt deve ter: objetivo, dono, modelo-alvo, variáveis, formato de saída, exemplos, limitações conhecidas e link para o dataset de avaliação. Categorize por domínio (código, suporte, dados) e por tipo (classificação, extração, geração, agente).

Testes automatizados de prompts

Rode o prompt contra um dataset a cada mudança (no CI) e falhe se a métrica cair abaixo do limiar. Combine checagens determinísticas (JSON válido? contém campo X? regex?) com avaliações por modelo.

Exemplo: teste de prompt com pytest

import json, pytest
from meu_app.prompts import classificar_ticket   # função que chama o LLM

CASOS = [json.loads(l) for l in open("prompts/classificar-ticket/evals/dataset.jsonl")]

@pytest.mark.parametrize("caso", CASOS, ids=lambda c: c["id"])
def test_classificacao(caso):
    saida = classificar_ticket(caso["entrada"])
    assert saida["categoria"] in {"bug", "financeiro", "outro"}   # formato
    assert saida["categoria"] == caso["esperado"]                # corretude

LangSmith Prompt Hub

O LangSmith oferece um Prompt Hub para armazenar, versionar (com commits e tags), comparar e testar prompts num playground, além de rodar avaliações sobre datasets e rastrear chamadas em produção. Alternativas: Langfuse, PromptLayer, ou um registry próprio no Git.

Query Reformulation e Prompt Enrichment

Em sistemas de busca e RAG, a pergunta do usuário muitas vezes é curta, ambígua ou usa palavras diferentes das do documento. Reformular a consulta antes de buscar melhora muito a recuperação.

Reformulação e enriquecimento de queries

  • Reescrita: transformar "e o prazo?" (com histórico) em "qual o prazo de cancelamento de pedidos?".
  • Expansão: adicionar sinônimos e termos técnicos.
  • Decomposição: quebrar perguntas compostas em sub-perguntas.
  • Multi-query: gerar várias versões e unir os resultados.

Query2Doc e HyDE

HyDE — Hypothetical Document Embeddings (paper): peça ao LLM para escrever um documento hipotético que responderia à pergunta, gere o embedding dele e busque documentos reais parecidos. Funciona porque "resposta se parece com resposta" mais do que "pergunta se parece com resposta".

Query2Doc (paper): gera um pseudo-documento e o concatena à query original (útil especialmente em busca por palavras-chave como BM25).

Exemplo: HyDE em poucas linhas

def hyde_search(pergunta, llm, embed, vector_db, k=5):
    hipotetico = llm(f"Escreva um parágrafo técnico que responda: {pergunta}")
    return vector_db.search(embed(hipotetico), k=k)   # busca pelo vetor da "resposta"

ITER-RETGEN

ITER-RETGEN (paper) alterna recuperação e geração em iterações: gera uma resposta parcial, usa essa resposta para fazer uma nova busca (que encontra informações que a pergunta original não alcançava), gera de novo… Útil para perguntas de múltiplos saltos ("qual linguagem usa o framework criado pela empresa X?").

Prompt Evaluation

Objetivos, métricas e tipos de avaliação

Antes de otimizar, defina critérios de sucesso específicos e mensuráveis (Define success criteria): "classificar corretamente ≥ 95% dos tickets", "respostas com menos de 150 palavras", "0 vazamentos de dados pessoais".

Tipo de avaliaçãoComo funcionaBom para
Correspondência exata / regexCompara com o esperadoClassificação, extração

Evaluators e Datasets

Dataset: conjunto de entradas (e, quando possível, saídas esperadas) que representa o uso real — inclua casos típicos, de borda e adversariais. Evaluator: a função que dá nota a cada saída. Comece com 20–50 casos bem escolhidos e cresça a partir de falhas reais de produção. Ver Create strong empirical evaluations e a ferramenta de avaliação do Console.

Embedding distance e critérios adicionais

Embedding distance: gera embeddings da resposta e da referência e mede a similaridade de cosseno — tolerante a paráfrases, mas não detecta erros sutis de fato ("aceita" vs "não aceita" podem ficar próximos). Por isso, combine com critérios adicionais: tamanho, presença de citações, ausência de PII, latência, custo.

Evaluation Comparativa

Precision, Recall e F1

Para tarefas de classificação/extração (ex.: "o prompt detecta tickets de fraude?"):

Precision = VP / (VP + FP)   → dos que marquei como fraude, quantos eram?
Recall    = VP / (VP + FN)   → das fraudes reais, quantas encontrei?
F1        = 2 · P · R / (P + R)   → média harmônica (equilíbrio)

Ex.: 100 tickets, 10 fraudes reais. O prompt marcou 12; 8 eram fraude.
VP=8, FP=4, FN=2 → Precision=0.67, Recall=0.80, F1≈0.73

Escolha a métrica conforme o custo do erro: em detecção de fraude, recall alto costuma importar mais; em alertas que acordam alguém de madrugada, precision.

Pairwise Evaluation

Em vez de dar nota absoluta, mostre duas respostas (prompt A × prompt B) para a mesma entrada e pergunte qual é melhor. É mais estável que notas de 1 a 10. Cuidado com o viés de posição: avalie também com a ordem invertida.

LLM-as-Judge

Use um modelo (de preferência forte) para avaliar saídas segundo uma rubrica explícita. Boas práticas: critérios objetivos, pedir raciocínio antes da nota, escala pequena (ex.: passa/não passa ou 1–5), e calibrar contra avaliações humanas.

Exemplo: juiz com saída estruturada

from pydantic import BaseModel
import anthropic

class Veredito(BaseModel):
    raciocinio: str
    fiel_ao_contexto: bool
    responde_a_pergunta: bool
    nota: int  # 1 a 5

client = anthropic.Anthropic()

def julgar(pergunta, contexto, resposta) -> Veredito:
    r = client.messages.parse(
        model="claude-opus-5-5",
        max_tokens=2000,
        system="Você é um avaliador rigoroso de respostas de um sistema RAG.",
        messages=[{"role": "user", "content": f"""
<pergunta>{pergunta}</pergunta>
<contexto>{contexto}</contexto>
<resposta>{resposta}</resposta>
Rubrica: fiel = toda afirmação é suportada pelo contexto;
responde = trata diretamente a pergunta. Raciocine e depois dê a nota."""}],
        output_format=Veredito,
    )
    return r.parsed_output
