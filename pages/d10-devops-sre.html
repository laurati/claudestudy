Disciplina 10

DevOps e SRE com IA

Pipelines gerados automaticamente, vulnerabilidades detectadas antes da produção, incidentes tratados com copilotos e agentes. A IA já está no fluxo de entrega e confiabilidade — do deploy à resposta a falhas.

Ao finalizar esta disciplina você será capaz de:

  • Automatizar deploys, pipelines e releases com suporte de IA
  • Integrar copilotos e agentes ao ciclo de confiabilidade
  • Identificar e resolver falhas com apoio de diagnósticos inteligentes
  • Aumentar a segurança com análise assistida de vulnerabilidades
  • Gerar resumos, alertas e postmortems com base em dados reais

Fundamentos de DevOps e SRE

Princípios e práticas do DevOps moderno

  • Cultura de responsabilidade compartilhada entre desenvolvimento e operações ("you build it, you run it").
  • Automação: CI/CD, infraestrutura como código (Terraform, Pulumi), GitOps (Argo CD, Flux).
  • Fluxo e feedback rápidos: lotes pequenos, deploys frequentes, observabilidade.
  • Métricas DORA: frequência de deploy, lead time de mudanças, taxa de falha de mudanças e tempo de recuperação.

O papel do SRE e a cultura de confiabilidade

Site Reliability Engineering (criado no Google) aplica engenharia de software a problemas de operação. Conceitos-chave:

SLI  (indicador)  → o que medimos       ex.: % de requisições com sucesso em < 300ms
SLO  (objetivo)   → a meta interna      ex.: 99,9% em 30 dias
SLA  (acordo)     → o contrato externo  ex.: 99,5%, com multa se violar
Error budget      → 100% − SLO = 0,1% ≈ 43 min/mês de "falha permitida"
                    → se sobrar budget: acelere releases; se acabar: priorize confiabilidade

Outros pilares: eliminar toil (trabalho manual repetitivo), postmortems blameless, on-call sustentável, planejamento de capacidade.

Automação de pipelines e deploys com IA

Geração assistida de pipelines e arquivos de configuração

Exemplo: prompt + pipeline gerado (GitHub Actions)

Gere um workflow GitHub Actions para este monorepo (Node 22, pnpm, Postgres nos testes):
- jobs paralelos: lint, typecheck, unit; e2e depende de unit
- cache de dependências; matriz só para unit (node 20 e 22)
- build da imagem Docker e push para GHCR apenas na main
- deploy em staging com aprovação manual para produção (environments)
Explique cada decisão em comentários curtos.
name: ci
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
  unit:
    runs-on: ubuntu-latest
    strategy:
      matrix: { node: [20, 22] }
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with: { node-version: "${{ matrix.node }}", cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm test
  # ... e2e (needs: unit), build-push (if: github.ref == 'refs/heads/main'), deploy
Revise pipelines gerados com atenção a: permissões do GITHUB_TOKEN (use permissions: mínimas), actions de terceiros (fixe por SHA), segredos expostos em logs e gatilhos como pull_request_target.

Otimização de etapas com base em histórico de builds e deploys

Exporte dados de execução (duração por job/step, taxa de falha, testes flaky) e peça análise: quais steps dominam o tempo, quais testes falham intermitentemente, onde o cache não está funcionando. A IA cruza padrões ("o job e2e falha 3× mais às segundas — coincide com o refresh do banco de staging").

Sugestões automáticas de ajustes e paralelizações

Exemplos típicos: dividir testes em shards, rodar jobs independentes em paralelo, cachear camadas Docker, pular jobs quando só a documentação mudou (paths-ignore), executar só testes afetados no monorepo.

Geração de changelogs e notas de release com copilotos

Exemplo: notas de release a partir dos commits

git log v2.3.0..HEAD --pretty="- %s (%h)" \
  | claude -p "Gere notas de release em português para usuários finais: agrupe em Novidades, Melhorias e Correções; omita commits internos (chore, ci, refactor); destaque mudanças incompatíveis."

Com Conventional Commits, ferramentas como release-please/semantic-release geram changelogs técnicos; a IA transforma em texto para o público certo.

Segurança em pipelines com IA

Introdução ao conceito de DevSecOps

DevSecOps integra segurança em todo o ciclo ("shift left"): verificações automáticas a cada commit/PR, em vez de uma auditoria no fim. Camadas: SAST (código), SCA (dependências), segredos, IaC, imagens de container, DAST (aplicação rodando).

Geração assistida de regras de SAST e DAST

A IA é ótima para escrever regras customizadas para padrões específicos do seu código.

Exemplo: regra Semgrep gerada para um padrão interno

# Prompt: "Crie uma regra Semgrep que detecte chamadas ao nosso cliente LLM
# passando input do usuário diretamente no system prompt."
rules:
  - id: user-input-in-system-prompt
    languages: [python]
    severity: WARNING
    message: >
      Entrada do usuário no system prompt facilita prompt injection.
      Coloque-a na mensagem de usuário, delimitada por tags.
    patterns:
      - pattern: llm.complete(system=$X, ...)
      - pattern-inside: |
          def $F(..., request, ...):
            ...
      - metavariable-pattern:
          metavariable: $X
          pattern-either:
            - pattern: request.$ATTR
            - pattern: f"...{request.$ATTR}..."

Para DAST (OWASP ZAP, Nuclei), a IA ajuda a gerar templates de varredura e cenários autenticados a partir do OpenAPI.

Automatização da detecção de vulnerabilidades via LLM

LLMs encontram classes de bugs que ferramentas baseadas em padrões não pegam (falhas de lógica de autorização, IDOR, condições de corrida) e reduzem ruído fazendo triagem de falsos positivos. Mas também geram falsos positivos — combine com ferramentas determinísticas e revisão humana. O Claude Code tem o comando /security-review e uma GitHub Action de revisão de segurança.

Validação de dependências e análise de pacotes com copilotos

  • Verificar se o pacote existe e é o oficial (combate a slopsquatting/typosquatting).
  • Avaliar saúde: manutenção, número de mantenedores, scripts de instalação suspeitos, licença.
  • Resumir CVEs do npm audit/Dependabot e priorizar pelo que é realmente alcançável no seu código.

Geração automatizada de alertas de segurança em pipelines

Ao final do pipeline, um passo de IA consolida achados de várias ferramentas, remove duplicatas, prioriza por severidade e exposição, e publica um comentário único no PR ou um alerta no canal de segurança — com contexto e sugestão de correção, em vez de 200 linhas de saída bruta.

Monitoramento e observabilidade assistidos por IA

Detecção de anomalias com explicação em linguagem natural

A detecção em si costuma ser estatística/ML (sazonalidade, desvio). A GenAI agrega a explicação: "a latência p99 do checkout subiu 4× às 14h05, logo após o deploy v2.4.1; o aumento está concentrado em chamadas ao serviço de frete, que passou a responder com timeout".

Consultas conversacionais a métricas e logs

Exemplo: linguagem natural → PromQL

Pergunta: "qual a taxa de erro 5xx do serviço checkout nos últimos 30 min, por rota?"

Gerado:
sum by (route) (rate(http_requests_total{service="checkout", status=~"5.."}[5m]))
/
sum by (route) (rate(http_requests_total{service="checkout"}[5m]))

Plataformas como Datadog, Grafana, New Relic, Dynatrace e Elastic já embutem assistentes; também é possível conectar um agente a Prometheus/Loki/Grafana via servidores MCP.

Insights e correlações automáticas com múltiplas fontes

O maior valor está em cruzar fontes que um humano olharia separadamente: deploys, feature flags, métricas, logs, traces, mudanças de infraestrutura, incidentes de provedores. Um agente com acesso de leitura a todas elas monta uma linha do tempo correlacionada.

Geração automatizada de resumos e dashboards

Resumos diários/semanais de saúde (SLOs, consumo de error budget, top erros), e geração de dashboards como código (JSON do Grafana, Terraform) a partir de uma descrição.

Resposta a incidentes com suporte de IA

Geração automática de resumos de incidentes

Durante um incidente, quem chega no meio precisa de contexto rápido. A IA lê o canal do incidente, alertas e timeline e produz: o que está acontecendo, impacto, hipóteses, o que já foi tentado, quem está fazendo o quê.

Sugestões de mitigação com base em runbooks e histórico

Com RAG sobre runbooks e postmortems anteriores, o copiloto sugere: "alerta semelhante em março (INC-231) foi resolvido aumentando o pool de conexões; runbook RB-12 passo 3". O humano decide e executa (ou aprova a execução).

Interações via ChatOps com copilotos operacionais

@sre-bot status checkout
  → SLO 99,2% (meta 99,9%) · budget restante: 12% · 3 alertas ativos · último deploy há 40 min (v2.4.1)
@sre-bot o que mudou na última hora?
  → deploy v2.4.1 (PR #812: novo cliente de frete) · flag "frete-v2" ativada para 50%
@sre-bot sugerir mitigação
  → desativar flag "frete-v2" (reversível, baixo risco) — [Aprovar] [Recusar]

Rascunhos automáticos de postmortem com base em dados reais

Exemplo: template de postmortem blameless + prompt

# Postmortem — INC-482: Lentidão no checkout
## Resumo            (2–3 frases)
## Impacto           (usuários afetados, duração, pedidos perdidos, SLO consumido)
## Linha do tempo    (UTC, com fonte de cada evento)
## Causa raiz        (técnica e contribuintes; "5 porquês")
## Detecção          (como descobrimos; quanto tempo levou)
## Resposta          (o que funcionou, o que não funcionou)
## Ações             (dono, prazo, tipo: prevenir / detectar / mitigar)
## Lições aprendidas

Prompt: "Com base na timeline exportada do canal #inc-482, nos alertas e nos
deploys anexados, preencha o template. Use linguagem blameless (sistemas e
processos, não pessoas). Marque [VERIFICAR] tudo que for inferência."

Agentes operacionais e copilotos

Diferença entre copilotos e agentes autônomos

CopilotoAgente autônomo
IniciativaResponde quando o humano pedeAge a partir de gatilhos (alertas, agenda)
AçõesSugere; humano executaExecuta (dentro de limites)
RiscoBaixoMaior — exige guardrails, auditoria, rollback

Exemplos de agentes atuando em diagnóstico e ações corretivas

  • Diagnóstico: ao disparar um alerta, o agente coleta logs, métricas, eventos do Kubernetes e mudanças recentes e posta um relatório inicial no canal — antes de o on-call abrir o notebook.
  • Correções de baixo risco: reiniciar um pod em CrashLoop conhecido, escalar réplicas dentro de limites, limpar disco de logs, desativar uma feature flag.
  • Higiene: abrir PRs para atualizar dependências vulneráveis, corrigir testes flaky, ajustar alertas ruidosos.

Estratégias de adoção gradual com supervisão humana

NívelO agente…Humano
0 — ObservadorSó lê e resumeDecide e executa tudo
1 — ConselheiroSugere ações com justificativaExecuta
2 — Executor supervisionadoExecuta após aprovação explícitaAprova cada ação
3 — Autônomo limitadoExecuta ações pré-aprovadas (allowlist, reversíveis) e reportaAudita; aprova o resto

Avance de nível por classe de ação, com base no histórico de acertos. Sempre: credenciais de menor privilégio, ações reversíveis, registro de auditoria, botão de "parar", e dry-run por padrão.

Casos práticos em ambientes com alta exigência de confiabilidade

  • Finanças/pagamentos: agente nível 0–1 durante incidentes; nenhuma ação automática em sistemas de liquidação; foco em reduzir o tempo de diagnóstico (MTTD/MTTR).
  • E-commerce em pico (Black Friday): autoscaling e feature flags com limites pré-aprovados (nível 3), mudanças de código congeladas.
  • Plataforma interna: agentes abrindo PRs de correção (nunca merge automático em produção sem revisão).
O livro Site Reliability Engineering do Google (gratuito online) continua sendo a base; a IA acelera as práticas, não as substitui.
