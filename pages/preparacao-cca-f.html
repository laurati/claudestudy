Domínio 1 — Arquitetura agêntica e orquestração (27%)

🎯 Objetivo

Desenhar agentes e sistemas multiagente que terminam, respeitam limites, sabem quando chamar um humano e não dependem só do prompt para obedecer regras.

🧩 Para que serve

É a diferença entre uma demo e um agente em produção: sem limites ele gasta sem parar; sem escalonamento ele inventa; sem enforcement por código ele "esquece" a regra no pior momento.

✅ Quando aplicar

Em todo agente que age no mundo real (reembolso, deploy, e-mail) e em qualquer orquestração com subagentes.

⛔ Erro comum na prova

Escolher "adicionar uma instrução mais enfática no system prompt" quando a alternativa correta é um hook, uma permissão ou uma validação em código.

O loop de tool use da Messages API

O modelo não executa ferramentas: ele pede. Sua aplicação executa e devolve o resultado. O campo stop_reason da resposta diz o que fazer em seguida:

stop_reasonSignificaSua aplicação deve
end_turnO modelo terminou a respostaEntregar ao usuário (o loop acaba)
tool_useO modelo quer chamar uma ou mais toolsExecutar todas as chamadas e devolver os tool_result na próxima mensagem
max_tokensA resposta foi cortada pelo limiteAumentar o limite ou continuar; não tratar como resposta completa
stop_sequenceEncontrou uma sequência de parada definida por vocêTratar conforme a lógica que definiu a sequência
pause_turnUma tool do servidor (ex.: web search) pausou um turno longoReenviar a conversa para o modelo continuar
refusalO modelo recusou por segurançaNão insistir com o mesmo pedido; tratar ou escalar

Exemplo: loop de agente com limite de passos e escalonamento (Python)

import anthropic
client = anthropic.Anthropic()
MAX_PASSOS = 8

def rodar_agente(pergunta: str) -> str:
    mensagens = [{"role": "user", "content": pergunta}]
    for passo in range(MAX_PASSOS):                      # loop sempre limitado
        resp = client.messages.create(
            model="claude-sonnet-5-5", max_tokens=2048,
            system=SYSTEM_PROMPT, tools=TOOLS, messages=mensagens,
        )
        mensagens.append({"role": "assistant", "content": resp.content})

        if resp.stop_reason == "end_turn":
            return texto(resp)
        if resp.stop_reason != "tool_use":
            return escalar_para_humano(mensagens, motivo=resp.stop_reason)

        resultados = []
        for bloco in resp.content:                       # pode haver várias chamadas em paralelo
            if bloco.type == "tool_use":
                resultados.append(executar_tool(bloco))  # devolve um bloco tool_result
        mensagens.append({"role": "user", "content": resultados})

    return escalar_para_humano(mensagens, motivo="limite de passos atingido")

Três pontos que a prova explora: (1) o loop tem teto; (2) todos os tool_use de uma resposta recebem um tool_result com o mesmo tool_use_id, na mesma mensagem; (3) qualquer saída inesperada termina em escalonamento, não em "tenta de novo para sempre".

Claude Agent SDK: o mesmo loop, pronto

O Claude Agent SDK é o harness do Claude Code como biblioteca (Python e TypeScript): ele já faz o loop, a execução de ferramentas (arquivos, terminal, web, MCP), a compactação de contexto, os subagentes, os hooks e as permissões. Você configura em vez de programar o loop.

Exemplo: agente com o Agent SDK (Python)

import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions

opcoes = ClaudeAgentOptions(
    system_prompt="Você investiga falhas de testes e propõe correções mínimas.",
    allowed_tools=["Read", "Grep", "Glob", "Bash"],   # menor privilégio
    permission_mode="default",                        # pede aprovação para o que não foi liberado
    max_turns=15,                                     # teto de iterações do loop
)

async def main():
    async for mensagem in query(prompt="Por que test_checkout falha?", options=opcoes):
        print(mensagem)

asyncio.run(main())

Versões recentes também aceitam um teto de custo por execução. Confira os nomes exatos das opções na referência do SDK da sua versão.

Passando contexto para subagentes: o subagente começa com contexto próprio e não vê a conversa do coordenador. O coordenador precisa passar explicitamente o objetivo, as restrições, o formato de retorno esperado e o que não fazer. O subagente devolve um resumo condensado, não tudo o que leu — é isso que economiza contexto.

Escalonamento para humano

Defina gatilhos objetivos, avaliados em código sempre que possível:

  • Valor ou risco: reembolso acima de R$ 500, exclusão de dados, mudança em produção.
  • Limites atingidos: passos, tempo ou custo.
  • Incerteza: falta informação, políticas conflitantes, o cliente pediu um humano.
  • Falhas repetidas: a mesma tool falhou várias vezes.

Ao escalar, entregue um resumo do caso (o que foi pedido, o que foi feito, o que falta e por que parou), para o humano não recomeçar do zero.

Enforcement: código × prompt

MecanismoGarantiaUse para
Instrução no system promptProbabilísticaTom, estilo, preferências, heurísticas
Descrição da tool / esquemaOrienta o uso; esquema valida formatoQuando e como chamar cada tool
Permissões (allow/deny), tools disponíveisDeterminísticaO que o agente pode fazer

Regra para a prova: se violar a regra causa dano real (dinheiro, dados, segurança, compliance), a resposta certa é um mecanismo determinístico. O prompt pode explicar a regra, mas não pode ser a única barreira.

Domínio 2 — Design de tools e integração MCP (18%)

🎯 Objetivo

Escrever tools que o modelo escolhe e usa corretamente, tratar erros de forma que o agente consiga se recuperar e configurar MCP com segurança.

🧩 Para que serve

A maioria dos "erros do agente" é, na verdade, tool mal descrita, sobreposta ou com erro opaco.

✅ Quando aplicar

Ao definir tools na API, ao escrever servidores MCP e ao conectar servidores de terceiros.

⛔ Erro comum na prova

Achar que o modelo "errou a tool" por falta de inteligência. A resposta costuma ser melhorar a descrição (quando usar, quando não usar, diferença para a tool vizinha).

Anatomia de uma boa tool

Exemplo: definição de tool com descrição completa

{
  "name": "buscar_pedido",
  "description": "Busca um pedido pelo número e devolve status, itens, valor e datas. Use quando o cliente citar um número de pedido ou perguntar sobre entrega/status. NÃO use para listar todos os pedidos do cliente (use listar_pedidos_cliente). Retorna erro NAO_ENCONTRADO se o número não existir.",
  "input_schema": {
    "type": "object",
    "properties": {
      "numero_pedido": {"type": "string", "description": "Número do pedido, só dígitos, ex.: "884123""}
    },
    "required": ["numero_pedido"]
  }
}
  • Descrição diz o que faz, quando usar, quando não usar e o que retorna.
  • Poucas tools, sem sobreposição. Duas tools que fazem quase a mesma coisa confundem a escolha.
  • Tools pela tarefa, não pelo endpoint: uma resumo_do_cliente é melhor que cinco GETs encadeados.
  • Retorno enxuto: só os campos úteis — resultado de tool ocupa contexto.

Erros de tool

Quando uma tool falha, devolva o erro ao modelo como resultado, marcado como erro, com informação suficiente para ele decidir o próximo passo:

{"type": "tool_result", "tool_use_id": "toolu_01A...", "is_error": true,
 "content": "NAO_ENCONTRADO: pedido 88412 não existe. Confirme o número com o cliente."}
Tipo de erroExemploO que fazer
TransitórioTimeout, 503, rate limit do sistema internoRetry automático no código com backoff, antes de envolver o modelo
Permanente / de entradaPedido inexistente, parâmetro inválidoDevolver com is_error e mensagem acionável; o modelo corrige ou pergunta ao usuário
Estado incertoTimeout num pagamento: cobrou ou não?Não repetir às cegas. Verificar o estado (consulta idempotente) ou escalar
PermissãoUsuário não pode ver aquele pedidoErro claro e sem vazar dado; o modelo informa o limite
Mensagens genéricas ("erro interno") fazem o modelo repetir a mesma chamada ou inventar uma resposta. Diga o que aconteceu e o que fazer.

MCP: o que a prova cobra além do básico

  • Handshake: o cliente envia initialize com versão do protocolo e capacidades; o servidor responde com as suas (ex.: suporta tools, resources, prompts, notificações de mudança na lista). Só depois o cliente chama tools/list e tools/call. Capacidade não declarada = recurso não usado.
  • Erros no MCP: falha de execução de tool volta como resultado com isError: true (o modelo vê); erro de protocolo (método inexistente, JSON inválido) volta como erro JSON-RPC (o cliente trata).
  • Transportes: stdio para servidores locais iniciados pelo cliente; Streamable HTTP para servidores remotos compartilhados, com autenticação (OAuth).
  • Escopos no Claude Code: local (só você, neste projeto), project (arquivo .mcp.json versionado para o time) e user (você, em todos os projetos). Segredos ficam em variáveis de ambiente referenciadas no .mcp.json, nunca no arquivo.
  • Confiança: conteúdo trazido por MCP é entrada não confiável (prompt injection). Servidor com credencial de escrita é ação com efeito real — aplique as mesmas permissões e hooks.

{

    "allow": ["Bash(npm run test:*)", "Bash(npm run lint)", "Edit(src/**)"],

Hooks

Comandos executados pelo harness em eventos do ciclo de vida: PreToolUse (antes de uma tool — pode bloquear), PostToolUse (depois — ex.: rodar o formatter), UserPromptSubmit, Stop e SubagentStop (ao terminar — ex.: exigir testes verdes), SessionStart, PreCompact, Notification. Um hook que sai com código 2 bloqueia a ação e devolve a mensagem ao agente. Exemplo completo na Disciplina 06; referência em Hooks.

Claude Code no CI/CD

Exemplo: modo não interativo e GitHub Action

# modo headless: uma tarefa, saída em JSON, ferramentas restritas, teto de turnos
claude -p "Revise o diff de origin/main...HEAD e liste problemas críticos" \
  --output-format json \
  --allowedTools "Read,Grep,Glob,Bash(git diff:*)" \
  --max-turns 10
# .github/workflows/claude-review.yml
name: Claude review
on: { pull_request: { types: [opened, synchronize] } }
permissions: { contents: read, pull-requests: write }
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: "Revise este PR seguindo o CLAUDE.md. Comente só problemas reais."

Princípios cobrados: permissões mínimas no token do workflow, chave em secret, ferramentas restritas, saída estruturada quando outro passo vai consumi-la e nada de merge automático. Ver GitHub Actions e headless.

Domínio 4 — Prompt engineering e saída estruturada (20%)

🎯 Objetivo

Escrever system prompts como especificação e obter saídas em formato garantido, validadas e com recuperação de erro.

🧩 Para que serve

Toda vez que outro programa consome a saída do Claude (extração, CI, integração), texto livre não serve: precisa de JSON válido e conferido.

✅ Quando aplicar

Cenários de extração estruturada e CI/CD; qualquer pipeline que grava a saída em banco ou chama outra API.

⛔ Erro comum na prova

Pedir "responda em JSON" no prompt e fazer json.loads torcendo para dar certo. O correto é esquema + mecanismo da API + validação.

A base de prompt engineering está na Disciplina 02. Pontos que a prova enfatiza: system prompt com princípios explicados (o porquê) em vez de dezenas de condicionais; exemplos few-shot variados; instruções diluídas num prompt enorme perdem força; prompts versionados e avaliados.

{"type": "tool", "name": "x"}Precisa usar exatamente a tool xExtração estruturada: a "tool" é só o esquema da saída
{"type": "none"}Não pode usar toolsPedir um resumo final sem novas ações

Com extended thinking ativado, só auto e none são aceitos. A API também tem o recurso de Structured outputs, que restringe a resposta a um JSON Schema — veja a documentação para os parâmetros da sua versão.

Exemplo: extração com tool forçada + validação + retry

import anthropic
from pydantic import BaseModel, ValidationError

class NotaFiscal(BaseModel):
    cnpj_emitente: str
    data_emissao: str          # AAAA-MM-DD
    valor_total: float
    itens: list[str]

FERRAMENTA = {
    "name": "registrar_nota",
    "description": "Registra os dados extraídos da nota fiscal.",
    "input_schema": NotaFiscal.model_json_schema(),
}
client = anthropic.Anthropic()

def extrair(texto_nota: str, tentativas: int = 2) -> NotaFiscal | None:
    mensagens = [{"role": "user", "content": f"<nota>{texto_nota}</nota>"}]
    for _ in range(tentativas + 1):
        r = client.messages.create(
            model="claude-haiku-5-5", max_tokens=1024,
            tools=[FERRAMENTA],
            tool_choice={"type": "tool", "name": "registrar_nota"},  # saída sempre no esquema
            messages=mensagens,
        )
        chamada = next(b for b in r.content if b.type == "tool_use")
        try:
            return NotaFiscal(**chamada.input)          # validação das regras do seu domínio
        except ValidationError as e:
            mensagens += [
                {"role": "assistant", "content": r.content},
                {"role": "user", "content": [{
                    "type": "tool_result", "tool_use_id": chamada.id, "is_error": True,
                    "content": f"Dados inválidos: {e}. Corrija só esses campos.",
                }]},
            ]
    return None   # esgotou: manda para revisão humana, não grava lixo

O padrão completo: esquema (formato) → validação (regras do domínio, ex.: CNPJ válido, soma dos itens) → retry com o erro específico → limite de tentativas → fila de revisão.

Batch API

A Message Batches API processa grandes volumes de forma assíncrona com cerca de 50% de desconto, com resultados em até 24 horas. É a resposta certa para "extrair dados de 200 mil documentos antigos" ou "classificar o histórico de tickets" — e a errada para qualquer coisa que um usuário espera na tela ou que bloqueia um PR.

Domínio 5 — Gestão de contexto e confiabilidade (15%)

🎯 Objetivo

Manter conversas e agentes longos dentro da janela, com custo controlado, e fazer o sistema continuar útil quando a API ou uma dependência falha.

🧩 Para que serve

Em produção, o problema raramente é a resposta do modelo — é o 429 no pico, a conversa que estourou o contexto ou a fatura que dobrou.

✅ Quando aplicar

Agentes de muitas etapas, chats longos, pipelines de alto volume, qualquer integração com SLA.

⛔ Erro comum na prova

Responder "usar um modelo com janela maior" para um problema de contexto mal gerenciado, ou "repetir até funcionar" para rate limit.

Orçamento de contexto

A cada chamada, a janela é dividida entre: system prompt + definições de tools + histórico + resultados de tools + documentos + espaço para a resposta. O que mais cresce sem controle são histórico e resultados de tools. Estratégias (detalhes em Context engineering):

  • Resultados de tool enxutos e paginados.
  • Compactação: resumir turnos antigos preservando decisões, pendências e identificadores.
  • Notas externas (arquivo de progresso) que o agente relê.
  • Subagentes para leituras extensas.
  • Informação crítica no início e reforçada perto do fim em prompts longos.

Prompt caching

Marque com cache_control o fim do trecho que se repete (tools, system prompt, documentos). Leituras do cache custam uma fração do preço normal e reduzem a latência. O cache só funciona com prefixo idêntico: deixe o que é fixo no começo e o que varia (pergunta do usuário, data/hora) no fim. Ver Prompt caching.

Rate limits e falhas da API

SituaçãoResposta correta
429 (rate limit)Retry com backoff exponencial + jitter, respeitando o header retry-after; fila para suavizar picos
529 (API sobrecarregada) / 5xxRetry com backoff; se persistir, degradar (modelo alternativo, resposta parcial, enfileirar)
400 (requisição inválida)Não repetir — corrigir a requisição
Falhas repetidas de uma dependênciaCircuit breaker: parar de chamar por um tempo e responder de forma degradada

Os SDKs oficiais já fazem retry automático com backoff para erros transitórios (configurável com max_retries). Ver Errors e Rate limits.

Degradação graciosa e proveniência

  • Se 3 de 5 fontes responderam, entregue o resultado parcial dizendo o que faltou, em vez de falhar tudo ou fingir completude.
  • Guarde a proveniência: de qual documento/tool veio cada afirmação, para auditoria e para o modelo citar.
  • Idempotência em ações: uma chave de idempotência evita cobrar duas vezes num retry.

Simulado (estilo cenário)

Questões no formato da prova: um cenário, quatro alternativas plausíveis, uma correta. Clique para ver a explicação.

1. Agente de atendimento. A política diz que reembolsos acima de R$ 500 exigem aprovação de um supervisor. Em testes, o agente aprovou sozinho um reembolso de R$ 800 em 2% dos casos, mesmo com a regra no system prompt. O que fazer?
Regra com impacto financeiro precisa de garantia determinística. O prompt pode explicar a regra, mas a barreira tem de estar no código.
2. Extração estruturada. Você extrai dados de contratos e às vezes o JSON vem sem o campo data_vigencia. Qual a abordagem mais robusta?
Esquema garante o formato; validação garante as regras; retry com o erro dá ao modelo o que corrigir; o limite evita loop infinito.
3. Claude Code para o time. O time quer que o agente nunca leia o arquivo .env, em nenhuma máquina. Onde configurar?
CLAUDE.md é instrução, não bloqueio. settings.local.json não é versionado. A regra deny no settings compartilhado vale para todos — e na política gerenciada não pode ser desfeita.
4. Pesquisa multiagente. O coordenador delega a 4 subagentes a análise de fontes diferentes. Os relatórios voltam com 20 mil tokens cada e o coordenador estoura o contexto ao consolidar. Qual a melhor correção?
O valor do subagente é isolar a leitura extensa e devolver só o que importa. max_tokens limita a saída, não a janela de entrada.
5. Tools. O agente chama listar_pedidos_cliente quando o cliente informa o número de um pedido específico, gerando respostas longas e lentas. Qual a primeira ação?
A descrição é o que o modelo usa para escolher. Forçar uma tool em todas as chamadas quebraria os outros fluxos.
6. Tools. A tool cobrar_cartao deu timeout. Não se sabe se a cobrança foi feita. O que o sistema deve fazer?
Estado incerto em ação com efeito real: verificar antes de agir, nunca repetir às cegas.
7. CI/CD. Você quer que o Claude Code revise cada PR no GitHub Actions e que um passo seguinte do pipeline leia os achados. Qual configuração?
Saída consumida por máquina deve ser estruturada; revisão não precisa de escrita; o teto de turnos controla custo e tempo.
8. Extração em massa. É preciso classificar 300 mil tickets antigos para um relatório que será lido na semana que vem. O que reduz mais o custo sem perder qualidade?
Sem urgência e em alto volume: batch (cerca de metade do preço). O prompt fixo repetido também se beneficia do caching.
9. Confiabilidade. No pico, parte das chamadas retorna 429. O que fazer?
Retry imediato piora o congestionamento. Backoff com jitter espalha as tentativas; a fila absorve a demanda.
10. Produtividade do dev. O time tem um procedimento de 2 páginas para criar migrações de banco, com um script de validação. É usado algumas vezes por semana. Onde colocar?
Procedimento longo, com arquivos de apoio e uso eventual é o caso típico de skill: só entra no contexto quando relevante. No CLAUDE.md custaria contexto em toda sessão.
11. Contexto. Um agente de suporte com system prompt de 6 mil tokens e 12 tools recebe milhares de conversas por dia. A conta está alta. Qual a primeira otimização?
Prefixo grande e idêntico em todas as chamadas é o caso ideal de caching. Data no início quebraria o cache; batch não serve para conversa em tempo real.
12. Arquitetura. Toda nota fiscal recebida passa por: extrair dados, validar CNPJ, lançar no ERP. Os passos nunca mudam. Qual arquitetura?
Passos fixos não precisam de um modelo decidindo a ordem. Workflow é mais barato, rápido e previsível.
