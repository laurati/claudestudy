Disciplina 08

Desenvolvimento de Agentes

Criar aplicações com IA é só o começo. Agentes definem objetivos, planejam, tomam decisões, executam ações e integram ferramentas externas de forma autônoma.

Ao finalizar esta disciplina você será capaz de:

  • Desenvolver agentes que assumem processos do início ao fim
  • Criar equipes de agentes coordenados, cada um com um papel diferente
  • Orquestrar agentes para executar fluxos complexos de forma autônoma
  • Escolher o framework ideal para cada tipo de agente
  • Transformar fluxos manuais em soluções automatizadas com agentes

Fundamentos de Agentes

O que são agentes e suas características

Um agente é um sistema em que um LLM dirige dinamicamente o próprio processo: decide quais ferramentas usar, em que ordem, e quando parar, com base no feedback do ambiente. Características:

  • Autonomia: escolhe os próximos passos.
  • Uso de ferramentas: APIs, bancos, código, navegador, outros agentes.
  • Percepção do ambiente: observa resultados e erros.
  • Persistência de objetivo: itera até concluir ou desistir de forma controlada.
  • Memória: curto prazo (contexto) e, opcionalmente, longo prazo.
┌──────────── loop do agente ────────────┐ Objetivo ─► LLM decide ─► chama ferramenta ─► observa resultado ─┐ ▲ │ └───────────────────── ainda não terminou? ◄────────────────┘ │ terminou ▼ resposta final

Diferenças entre aplicações com IA e agentes autônomos

Aplicação com IA (workflow)Agente autônomo
Quem define os passosO códigoO LLM, em tempo de execução
PrevisibilidadeAltaMenor
Custo/latênciaBaixos e previsíveisMaiores e variáveis
Ideal paraTarefas bem definidasTarefas abertas, multi-passo, difíceis de prever
Antes de construir um agente, pergunte: a tarefa é complexa e difícil de especificar? O valor justifica o custo? O modelo é capaz? Erros podem ser detectados e corrigidos? Se alguma resposta for "não", prefira um workflow (Building effective agents).

Ciclo de vida: objetivo, plano, execução, adaptação

  1. Objetivo: recebido do usuário ou de um gatilho (evento, agenda).
  2. Plano: decompõe em passos (explícito, num "todo list", ou implícito).
  3. Execução: chama ferramentas, coleta resultados.
  4. Adaptação: replaneja diante de erros ou informações novas; pede ajuda humana quando necessário; encerra com um relatório.

Tipos de agentes: baseados em ferramenta, com memória, reflexivos

  • Baseados em ferramenta: o núcleo é o loop de tool use (ex.: agente de suporte que consulta pedidos).
  • Com memória: lembram preferências e fatos entre sessões (memória de longo prazo em banco/arquivos).
  • Reflexivos: avaliam e criticam a própria saída antes de entregar (reflection / evaluator-optimizer).

Visão Geral de Frameworks

Estilos de agentes: stateful, conversacional, por papéis e com planejamento

  • Stateful (grafo de estados): fluxo modelado como grafo com estado explícito e checkpoints — LangGraph.
  • Conversacional: agente de chat com ferramentas e memória — LangChain agents, ADK.
  • Por papéis (role-based): "equipe" de agentes com papel, objetivo e backstory — CrewAI.
  • Com planejamento: um planner gera o plano, executores seguem — padrões plan-and-execute.

Criando seu Primeiro Agente com ADK

Panorama de frameworks e escolha do ADK (Google)

O Agent Development Kit (ADK) é o framework open source do Google para construir, avaliar e implantar agentes. Pontos fortes: estrutura "code-first" clara, interface de desenvolvimento (adk web), multiagente nativo, sessões/estado bem definidos, integração com A2A e Vertex AI. O curso o usa como framework principal pelos conceitos explícitos de runtime.

Preparação do ambiente e configuração da Google API

  1. Python 3.10+ e um ambiente virtual.
  2. Crie uma chave no Google AI Studio (ou configure Vertex AI no Google Cloud).
  3. Guarde a chave num .env (nunca no código).

Instalação do Google ADK

Criação do primeiro agente com instruções e modelos

Exemplo: agent.py

from google.adk.agents import Agent

def consultar_status_pedido(pedido_id: str) -> dict:
    """Consulta o status de um pedido.

    Args:
        pedido_id: identificador no formato PED-123.
    Returns:
        dict com status ("ok"/"erro") e dados do pedido.
    """
    pedidos = {"PED-123": {"status": "ENVIADO", "previsao": "2026-11-20"}}
    if pedido_id not in pedidos:
        return {"status": "erro", "mensagem": f"Pedido {pedido_id} não encontrado"}
    return {"status": "ok", "pedido": pedidos[pedido_id]}

root_agent = Agent(
    name="atendente_pedidos",
    model="gemini-2.5-flash",
    description="Responde dúvidas sobre status de pedidos.",
    instruction=(
        "Você é um atendente cordial. Use a ferramenta consultar_status_pedido "
        "sempre que o cliente mencionar um pedido. Nunca invente status."
    ),
    tools=[consultar_status_pedido],
)
adk web            # interface de desenvolvimento no navegador
adk run meu_agente # conversa pelo terminal
Usando Claude no ADK: o ADK aceita outros modelos via LiteLLM: from google.adk.models.lite_llm import LiteLlm e model=LiteLlm(model="anthropic/claude-opus-5-5") (com ANTHROPIC_API_KEY no ambiente).

Tools: Dando Capacidades ao Agente

O que é uma Tool e como criar uma boa Tool

Uma tool é uma função que o agente pode chamar. No ADK, funções Python viram tools automaticamente: o nome, a docstring e os tipos dos parâmetros viram a descrição que o modelo lê. Boas práticas (válidas para qualquer framework — ver Writing effective tools for agents):

  • Nome e descrição claros: o que faz, quando usar, formato dos parâmetros.
  • Poucas tools, sem sobreposição; prefira tools de alto nível ("agendar_reuniao") a várias de baixo nível.
  • Retorne dados concisos e relevantes (não o JSON inteiro de 500 campos).
  • Erros acionáveis: "data deve estar no formato AAAA-MM-DD", não "erro 400".
  • Retornos estruturados com status explícito.

Fluxo de invocação de uma Tool

1. Usuário: "Cadê meu pedido PED-123?" 2. LLM gera uma function_call: consultar_status_pedido(pedido_id="PED-123") 3. Runtime executa a função Python 4. Resultado (function_response) é adicionado ao contexto 5. LLM gera a resposta final usando o resultado

Execução de agentes com ADK Web

adk web abre uma interface onde você conversa com o agente e inspeciona cada evento: chamadas de ferramentas com argumentos, respostas, mudanças de estado e o trace completo — indispensável para depurar.

Aprovação de execução de Tools

Ações sensíveis (pagamentos, e-mails, deleções) devem exigir confirmação humana. No ADK isso pode ser feito com callbacks (ex.: before_tool_callback, que inspeciona a chamada e pode bloqueá-la) e, nas versões recentes, com o mecanismo de confirmação de tools. O princípio vale para qualquer framework: o agente propõe, o humano aprova.

Exemplo: callback que bloqueia reembolsos acima de um limite

def checar_permissao(tool, args, tool_context):
    if tool.name == "emitir_reembolso" and args.get("valor", 0) > 500:
        return {"status": "bloqueado",
                "mensagem": "Reembolsos acima de R$ 500 exigem aprovação de um supervisor."}
    return None   # None = segue com a execução normal

root_agent = Agent(..., tools=[emitir_reembolso], before_tool_callback=checar_permissao)

Subagentes e Coordenação

Fundamentos e primeiros exemplos de subagentes

Em vez de um agente gigante com 30 ferramentas, crie agentes especializados e um coordenador. Cada subagente tem instrução e ferramentas próprias — menos confusão, melhor desempenho.

Exemplo: coordenador com subagentes no ADK

from google.adk.agents import Agent

financeiro = Agent(name="financeiro", model="gemini-2.5-flash",
    description="Trata boletos, reembolsos e cobranças.",
    instruction="Resolva questões financeiras usando as ferramentas.",
    tools=[segunda_via_boleto, emitir_reembolso])

logistica = Agent(name="logistica", model="gemini-2.5-flash",
    description="Trata status de entrega, rastreio e trocas.",
    instruction="Resolva questões de entrega.",
    tools=[consultar_status_pedido, rastrear])

root_agent = Agent(name="coordenador", model="gemini-2.5-flash",
    description="Atendimento geral da loja.",
    instruction="Entenda a necessidade e transfira para o especialista adequado.",
    sub_agents=[financeiro, logistica])

Transferência de controle entre agentes (transfer to agent e autoflow)

Com sub_agents, o ADK habilita a delegação dirigida pelo LLM (AutoFlow): o modelo do coordenador pode chamar transfer_to_agent(agent_name="financeiro") com base nas description dos subagentes — por isso descrições claras são essenciais. A transferência passa o controle da conversa ao subagente. Alternativa: AgentTool, que usa um agente como ferramenta (o coordenador chama, recebe o resultado e continua no controle).

Coordenação entre agente coordenador e subagentes

  • Delegação (transfer): o especialista assume a conversa.
  • Agente como ferramenta (AgentTool): o coordenador mantém o controle e sintetiza.
  • Workflow agents (determinísticos): SequentialAgent (um após o outro), ParallelAgent (simultâneos), LoopAgent (repete até condição) — combinam bem com LLM agents.
  • Estado compartilhado: agentes trocam dados via session.state (ex.: output_key grava a saída de um agente no estado para o próximo ler).

Modos de agente: chat, single turn e task

Sessões, Aplicações e Execução (Runtime do ADK)

Arquitetura do runtime do ADK: sessões, apps e runners

  • Agent: a lógica (instrução, modelo, ferramentas).
  • App: identificada por app_name; agrupa agente(s) e configuração.
  • Session: uma conversa — histórico de eventos + state (dicionário chave/valor) para um user_id.
  • SessionService: onde as sessões vivem (memória, banco, Vertex AI).
  • Runner: orquestra a execução — recebe a mensagem, roda o agente, emite eventos, persiste na sessão.

Construção de uma aplicação web agêntica

Exemplo: expondo o agente via FastAPI

from fastapi import FastAPI
from google.adk.runners import Runner
from google.adk.sessions import DatabaseSessionService
from google.genai import types
from meu_agente.agent import root_agent

APP = "atendimento"
sessions = DatabaseSessionService(db_url="sqlite:///./sessoes.db")   # persistência
runner = Runner(agent=root_agent, app_name=APP, session_service=sessions)
api = FastAPI()

@api.post("/chat/{user_id}/{session_id}")
async def chat(user_id: str, session_id: str, texto: str):
    if not await sessions.get_session(app_name=APP, user_id=user_id, session_id=session_id):
        await sessions.create_session(app_name=APP, user_id=user_id, session_id=session_id)

    msg = types.Content(role="user", parts=[types.Part(text=texto)])
    resposta = ""
    async for evento in runner.run_async(user_id=user_id, session_id=session_id, new_message=msg):
        if evento.is_final_response() and evento.content:
            resposta = evento.content.parts[0].text
    return {"resposta": resposta}

Padrão assíncrono, generators e event loop

run_async é um async generator: em vez de devolver uma resposta pronta, ele emite eventos à medida que acontecem (chamada de ferramenta, resultado, texto parcial, resposta final). Isso roda no event loop do asyncio, permitindo atender muitas sessões concorrentes sem bloquear enquanto espera o LLM ou as ferramentas, e facilita streaming para o frontend (SSE/WebSocket).

Persistência de sessão em banco de dados

InMemorySessionService é só para desenvolvimento (perde tudo ao reiniciar). Em produção use DatabaseSessionService (SQLAlchemy: SQLite, PostgreSQL, MySQL) ou o serviço gerenciado do Vertex AI. Assim o usuário retoma a conversa depois e você tem auditoria.

Gerenciamento de estado e output schema

  • state: dicionário da sessão. Prefixos definem escopo: sem prefixo (sessão), user: (todas as sessões do usuário), app: (toda a app), temp: (só a invocação atual).
  • Instruções podem interpolar estado: instruction="O cliente prefere {user:idioma}."
  • output_schema: força o agente a responder num formato (modelo Pydantic) — útil para agentes "single turn" em pipelines.
  • output_key: grava a resposta do agente no estado para o próximo agente.

Exemplo: extrator com output_schema

from pydantic import BaseModel
from google.adk.agents import Agent

class Triagem(BaseModel):
    categoria: str      # financeiro | logistica | outro
    urgente: bool

triador = Agent(name="triador", model="gemini-2.5-flash",
    instruction="Classifique a mensagem do cliente.",
    output_schema=Triagem, output_key="triagem")   # resultado vai para state["triagem"]

Observabilidade do Agente

Painel do ADK e visualização de execução em tempo real

O adk web mostra, para cada turno, a sequência de eventos, a árvore de chamadas entre agentes, argumentos e retornos das ferramentas e o estado da sessão. É o equivalente ao "debugger" do agente.

Rastreamento de ações, decisões e uso de ferramentas

Em produção, exporte traces via OpenTelemetry (o ADK tem integração; também Cloud Trace, LangSmith, Langfuse, Arize Phoenix). Registre por execução: agente, ferramentas chamadas, latência, tokens, erros, transferências entre agentes.

Registro de histórico e refinamento do comportamento

Transforme sessões reais em datasets de avaliação: conversas que deram errado viram casos de teste. O ADK tem suporte a avaliação (adk eval) com arquivos de casos que verificam trajetória (ferramentas esperadas) e resposta final. Ciclo: observar → identificar falha → ajustar instrução/tool → rodar eval → implantar.

2. Para que serve o Runner?
Agent = lógica; SessionService = armazenamento; Runner = execução.
3. Um fluxo fixo "extrair → validar → salvar" sem decisões abertas deve ser…
